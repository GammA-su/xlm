## 3. Canonical membership identity (`xlm-canonical-train-membership-v1`)

`xlm.data.ordering.membership.build_membership(readers)` streams each verified
source shard (`offsets.jsonl` + `tokens.bin`, after `verify_integrity()`):

- **Per document** (`member_digest`): SHA-256 of canonical JSON of
  `{version, index, token_dtype, token_sha256}` where `index` is the full
  `offsets.jsonl` record **minus positional fields** (`token_start`,
  `byte_start`, `byte_end`). It therefore binds doc id, source id, lineage id,
  split, split group, token/byte counts, per-token byte spans, BOS/EOS
  positions and valid targets, plus the SHA-256 of the document's exact token
  bytes.
- **Per source**: `membership_digest` = SHA-256 over `[doc_id, member_digest]`
  lines **sorted by doc id**, plus document/token/byte counts.
- **Membership**: `canonical_membership_id = identity_digest({membership_version,
  split: "train", tokenizer_hash, sources: {id: {document_count, token_count,
  byte_count, membership_digest}}})`.

Refusals: any `split != "train"` record (code `membership_split_violation`),
duplicate doc ids, a record naming another source, non-contiguous index,
payload/index/manifest disagreement, mixed tokenizers, a shard whose checksum
fails, more than 20,000,000 documents. The same documents written in reverse
physical order give **different shard checksums but the identical membership
id**; a missing, extra, content-changed (including same-length), lineage-changed
or source-moved document gives a different id (tests §12). Text-level
`clean_hash` is not propagated into token shards, so content identity is
token-level under the bound tokenizer (a tokenizer change is a new membership).

## 4. Order manifest (`m5-independent-document-order-v1`)

```json
{"manifest_version": "m5-independent-document-order-v1",
 "within_source_order_policy": "m5_within_source_document_permutation_v1",
 "derivation": {"algorithm": "sha256_keyed_sort_permutation_v1", "order_seed": 35051},
 "canonical_membership_id": "<sha256>", "canonical_membership": {<membership summary>},
 "invariants": {split, granularity whole_document, content unchanged, within_source_only,
                mixture unchanged, epochs replay the same order, runtime_shuffle none},
 "sources": {"<source>": {"shard": {shard_id, source_id, checksum_sha256,
             offsets_checksum_sha256, num_tokens, num_documents, token_dtype, tokenizer_hash},
             "document_count": n, "token_count": t,
             "ordered_doc_ids_digest": "<sha256 of the ordered id sequence>",
             "ordered_doc_ids": ["..."]}},
 "order_manifest_id": "<identity_digest(header)>"}
```

- The **header** is the manifest without `ordered_doc_ids` (bound by their
  digest) and without its id. `order_manifest_id = identity_digest(header)`
  (sorted-key canonical JSON, so JSON key order is irrelevant).
- `verify_order_manifest` checks the header shape/versions/invariants, that
  `canonical_membership_id` recomputes from the embedded summary, the counts,
  the id, each sequence digest, that each list is a permutation of its count
  **and that each list equals the seed's derivation** (a hand-edited order with
  recomputed digests is refused).
- `load_order_manifest(path, expected_id=...)` is bounded (512 MiB) and pins the
  id. `write_order_manifest` is atomic and never overwrites.

## 5. Derivation, same seed, different seed

Within source `s`, documents sort ascending by
`SHA-256(json([algorithm, order_seed, canonical_membership_id, s, doc_id]))`,
doc id tie-break. No global RNG, Python `hash`, filesystem order or time is
involved; keys depend only on document identity, so the physical shard order is
irrelevant (tested with reversed shards and with `PYTHONHASHSEED=0/12345`
subprocesses). A sort by 256-bit pseudorandom keys is a uniform permutation up
to key collisions (< n²/2²⁵⁷).

- **Same seed**: identical manifest, sequences and id (tested).
- **Different seed** (authored fixture, seeds 35051/35052): same membership id,
  different ids, every source's sequence differs:

  | source | order A (35051) | order B (35052) |
  |---|---|---|
  | alpha | 0, 3, 4, 1, 2, 5 | 5, 1, 3, 2, 0, 4 |
  | beta | 0, 1, 3, 4, 2 | 4, 3, 2, 0, 1 |

- **Not independent** (`independence_problems`): same manifest, different
  memberships (even with equal counts), a shared seed, or **any source with ≥2
  documents whose sequence is identical** (e.g. the same sequence relabelled
  with another seed). Policy for tiny memberships: a colliding seed is
  **rejected; choose another seed** (a 2-document-per-source collision is found
  and refused in a test).

## 6. Whole-document integrity and split firewall

`OrderedSourceIndex` serves a virtual per-source stream = whole documents
concatenated in manifest order, reading each document's own contiguous
physical span of the unchanged `tokens.bin`. Tests compare, for every document
under both orders, the tokens read through the index with the physical tokens,
and the returned index record with the physical record (identical except
`token_start`, rebased to the virtual position; `physical_token_start` keeps the
original). Shard bytes and checksums are unchanged afterwards. No
retokenization, normalization, fragment interleaving or token shuffle exists.

Split firewall: membership refuses any non-train record; the index refuses a
non-train shard; a manifest naming a doc id not in the membership fails
permutation/derivation checks. A manifest built over mixed train/validation
membership therefore cannot be produced or used.

## 7. Storage representation and byte overhead

Index-only: two orders are two small JSON files beside the **unchanged** shard
payload; no `tokens.bin` is copied (tested: shard files byte-identical, no
token payload under the orders directory). Measured:

| Case | Bytes |
|---|---:|
| Authored fixture token payload (`tokens.bin`, 11 short docs) | 1,102 |
| Authored fixture `tokens.bin` + `offsets.jsonl` | 9,875 |
| Order manifest A / B (fixture, includes fixed header) | 2,912 / 2,912 |
| Synthetic ids `alpha_000123`, 1k / 10k / 100k docs | 19,276 / 175,790 / 1,830,804 |
| Marginal cost per document per order (12-char ids) | ≈ 18.4 |

The overhead scales with **document count**, not tokens: about (id length + 6)
bytes per document per order. The tiny fixture documents make the fixture ratio
unrepresentative. The 2 GiB frozen-shard cap is unchanged; order manifests are
not counted in it and have their own 512 MiB bound. Real Mix-01 overhead is NOT
MEASURED (no real shards).

## 8. Stream and producer integration

- `MixtureBatcher(..., document_order=<verified manifest>)` verifies the manifest
  (including derivation), requires its sources and shard identities to equal
  the bound readers, and routes `_read`/`_document_at` through
  `OrderedSourceIndex`. Cursors are positions in the ordered stream; the stream
  code, packer, scheduler, exposure plan and trace are otherwise unchanged. The
  per-target `token_offset` in the trace is the ordered-stream position.
- Without an order nothing changes: shard-native states carry no new key, so
  their bytes, digests and resume behavior are identical (the whole existing
  stream/prefetch/trace suite passes).
- **Quotas unchanged** (tested with a frozen exposure plan): identical update
  sizes and exactly the planned per-source totals under native, A and B; the
  exposure-plan identity is the same. Per-window valid targets depend on where
  document boundaries fall (a BOS label is never a target; document caps end a
  visit), so the realized window interleaving may differ between orders;
  per-source cumulative counts stay within two windows of the native run. The
  scheduler algorithm, weights, exhaustion and repeat policy are untouched.
- **Epochs** replay the same frozen order (no reshuffle); repeated targets are
  counted as before. Global RNG state is irrelevant (tested).
- **Producer**: `ProducerSpec` carries `document_order`; `build()` (what the P34
  child executes) verifies and indexes the same order. Tested: `spec.build()`
  yields identical batches; a real spawned `PrefetchingBatcher` child served 6
  updates whose per-target doc ids and input ids equal the synchronous batcher's
  and whose committed states are equal (the torch conversion of a prepared update
  was replaced by identity because torch is absent; child, pipe protocol, state
  binding and content verification were real). A forged order is refused at
  `build()`.

## 9. Execution identity, checkpoint and exposure receipts

- **Config**: `data.document_order: {manifest (absolute), order_manifest_id,
  canonical_membership_id}` — pins only, never `latest`. `normalize_training_data`
  requires `training.science_version`. `resolve_training_input` loads the pinned
  manifest, recomputes the shards' membership, checks it against the manifest and
  passes the manifest to the batcher (`MixtureInput.document_order`).
- **Envelope/identity**: the reference is in the resolved config (so in the
  envelope, plan hash and execution hash), and `bindings.data` gains
  `document_order: {order_manifest_id, canonical_membership_id}` **only when an
  order is bound**, so legacy and pre-M5 data identities keep their bytes.
- **Data state / checkpoint / exposure**: committed state gains
  `document_order: {order_manifest_id, canonical_membership_id,
  within_source_order_policy}` (only for ordered streams). It is saved as
  `data_state.json`, and therefore also in the M3 `data_cursor_digest` and the P34
  producer's state digests.
- **Resume**: `MixtureBatcher.load_state` refuses a state whose order identity
  differs (A→B, A→native, native→A) and restores nothing. `CheckpointManager.
  load_checkpoint` step 2c compares the checkpoint's `data_state.json` order
  identity with the current batcher **before model, optimizer, schedule, scaler or
  data state are restored** (`IncompatibleCheckpointError`). Frozen runs are
  refused even earlier by the envelope check.
- **Forks**: checkpoint forks keep the data lineage (cursors are ordered-stream
  positions), so they also refuse another order, exactly as the stream already
  refuses a changed mixture. Selecting order B is a **new experiment**: a fresh
  run whose config pins B and so gets a new envelope/execution identity.
- Pre-M5 science-v1 checkpoints carry no order key and resume under their
  original identity (the shard-native path is byte-identical).

## 10. M4 integration

- **Evidence v2** (`xlm-science-run-evidence-v2`): `order_manifest_id`,
  `canonical_membership_id` and `within_source_order_policy` come from the
  receipts. The envelope's pinned `data.document_order` and the committed
  `data_state.document_order` must agree; both absent → pre-M5 sentinels
  (`shard_native_no_order_manifest`, `canonical_membership_not_bound_pre_m5`,
  `shard_native_offset_order_v1`); any disagreement is **refused**, never replaced
  by the sentinel. v1 records stay verifiable and read (without rewriting) as
  pre-M5 via `evidence_fields`.
- **Tracks** (`xlm-science-tracks-v2`): new field `canonical_membership_id`,
  MUST_MATCH on every track. Microbatch pairs must share order and membership
  (pairing already required the order id). Mixture comparisons keep the order
  policy fixed; an undeclared policy difference is INELIGIBLE. The checked-in
  comparison drafts list the new invariant.
- **Robustness slot**: `order_robustness` now *verifies* the declaration
  (`science_order.declaration_problems`) and the run binding
  (`run_binding_problems`) before SATISFIED. The paired t statistics,
  Bonferroni, margins, decisions, sample sizes and promotion states are
  unchanged; only `CandidateEvidence` gained the per-tuple membership receipts.
  M4's promotion tests now build their M5 slot from real authored order headers
  instead of simulated ids.

### Order declaration (the `m5_order_evidence` slot)

`{kind: m5_independent_order_manifests_v1, canonical_membership_id,
order_manifests: [verifiable headers], order_manifest_ids, allocation_policy:
m5_alternating_roster_allocation_v1, allocation: {tuple_id: order_id}}`. Valid
only if every header verifies, the ids are those headers' distinct ids, all order
the declared membership, every pair is independent (§5), the allocation covers
every roster tuple and follows the policy, and every roster entry carries its
allocated order. SATISFIED additionally needs every complete pair's receipts to
carry its allocated order and the declared membership, spanning ≥2 orders.

### Allocation (§H)

Tuple *i* in roster order → order *i* mod *k*. Five-pair 50M: **C0/C2/C4 → A,
C1/C3 → B** (validated). Three-tuple 150M/300M blocks: A/B/A (both orders
covered). All five on A is refused (policy and fewer than two orders).

   planning resolves the input up to three times. Real 2 GiB cost is unmeasured.

   INELIGIBLE, because one order manifest binds the whole membership. A

   stricter than "a fork may select B", and consistent with the mixture rule.
7. Legacy (no envelope, no order) domain-API resumes still cannot detect a
   same-label re-prepared shard (audit row 13); unchanged for legacy.

   the full manifest is used (planning, stream, producer). A run can only carry
   an order id that its stream accepted.
9. Evidence/track versions moved to v2; tools pinned to the v1 strings must be
