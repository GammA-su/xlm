## 1. Pre-change order audit (written before any product edit)

Read from the code at `221c4e0`. Paths are under `src/xlm/`.

| # | Question | Finding |
|---|---|---|
| 1 | Where canonical document membership is represented | Upstream: frozen pool manifests (`data/pools/manifest.py`: `compute_membership_digest` over sorted doc ids + split, `compute_content_digest` over `doc_id:clean_hash`). **At the training boundary** membership exists only implicitly, as the set of records in each source token shard's `offsets.jsonl` (`data/tokens.py::TokenShardWriter`). No training-side membership identity exists; the pool digests are not carried into token shards, the execution envelope or checkpoints. |
| 2 | Stable document identifier | `doc_id` (C02 `CanonicalDocument.doc_id`), written per record into `offsets.jsonl` together with `source_id`. Nothing enforces uniqueness of `doc_id` within a shard. |
| 3 | Is shard order deterministic | Yes, given identical inputs: `TokenShardWriter.write_documents` writes documents in the caller's iteration order, and `data/datasets/shards.py` rolls canonical shards by source record order and size only. The physical order is therefore a by-product of preparation, not a declared scientific choice. |
| 4 | Does preparation record document order | Only implicitly: each `offsets.jsonl` record carries `token_start`/`byte_start`/`byte_end` (cumulative positions), and `offsets_checksum_sha256` binds that file. There is no order seed, order policy, order identity or ordered-id list. |
| 5 | What `data_seed` changes | `QuotaScheduler.source_ids` tie order (`blake2b(seed:source)`), the exposure plan's residual apportionment ranking and `source_order` (`data/sampling/plan.py::_order_key`), and `MixtureRecipe.identity()`. |
| 6 | Does it change within-source document order | **No.** `MixtureBatcher._next_window` reads increasing token offsets `cursor → cursor+take` from `tokens.bin`; a new epoch restarts at offset 0. No code permutes documents within a source. |
| 7 | How offsets/token spans bind documents | `offsets.jsonl` record: `token_start`, `token_count` (contiguous, validated by `training/inputs.py::_validate_training_index`), `byte_count`, `covered_bytes`, per-token `token_byte_spans` (document-local canonical byte coordinates), `byte_start`/`byte_end` (shard-cumulative), `valid_targets`, `bos_positions`/`eos_positions` (document-local), `lineage_id`, `split_group`, `split`. `MixtureBatcher._document_at` maps a token position to its record by streaming the index; `_pack_window` derives per-target `doc_ids`, `lineage_ids`, `byte_spans`, `token_offsets`. |
| 8 | Split and lineage | `split` per record (C02: `train`/`diagnostic_val`/`audit`); `lineage_id = cluster_ids["duplicate_cluster"]`, `split_group = cluster_ids["split_group"]`. The training firewall is `_validate_training_index`, which refuses any record whose `split != "train"`. M3 adds a held-out doc-id overlap check for the pilot. |
| 9 | Hashes identifying a shard | `TokenShardManifest`: `checksum_sha256` (tokens.bin), `offsets_checksum_sha256` (offsets.jsonl), `num_tokens`, `num_documents`, `tokenizer_hash`, `pool_hash`, `shard_id`, `source_id`, `token_dtype`; plus the SHA-256 of `shard_counters.json` in the data identity. Both checksums depend on the physical order. |
| 10 | How exposure plans reference shards | By `source_id` and availability counts only (`SourceAvailability` from `shard_counters.json`); `mixture_identity` includes component `shard_id` labels. No checksum. The plan dict is the `exposure_identity` (`identity_digest`). The execution binding `bindings.data = identity_digest({sources: {manifest, counters sha}, mixture, exposure})`. |
| 11 | How resume binds data state | `data_state.json` = `MixtureBatcher.get_state()` (committed): `version`, `mixture_identity`, `exposure_identity`, per-source `cursors` (**physical token offsets into tokens.bin**), `epochs`, `carry_token`, scheduler counters, `committed_valid_targets`, chained `trace_digest`. `load_state` checks version, mixture identity and exposure identity only. Frozen runs also require the identical envelope (which binds shard checksums through `bindings.data`). |
| 12 | Where M4 gets `order_manifest_id` / `within_source_order_policy` | **Constants**, not receipts: `comparison/science_evidence.py` writes `ORDER_SENTINEL = "shard_native_no_order_manifest"` and `WITHIN_SOURCE_ORDER_POLICY = "shard_native_offset_order_v1"` for every run. `science_promotion.order_robustness` accepts any manifest slot of kind `m5_independent_order_manifests_v1` naming ≥2 distinct ids that the runs carry — the ids are self-declared, their membership is never checked. |
| 13 | Could ordinary resume switch to a differently ordered artifact unnoticed | **Frozen path: no** — a re-prepared shard with another physical order has another `checksum_sha256`, so `bindings.data` and the envelope differ and ordinary resume is refused. **Domain-API path (no envelope): yes** — `load_state` compares only mixture/exposure identities, which depend on labels and counts; a same-label, same-count shard in another physical order is accepted and the saved cursors then index a different document sequence. |
| 14 | Can identical membership / different order be represented without rewriting the producer | **Yes.** The stream touches documents only through `_read(source, start, count)` and `_document_at(source, position)`, in per-source cursor coordinates. An ordered-document index can present a *virtual* per-source token stream (documents concatenated in manifest order) over the unchanged `tokens.bin`/`offsets.jsonl`. The P34 producer child rebuilds the same `MixtureBatcher` from a plain `ProducerSpec`; carrying the frozen order manifest in that spec gives the child exactly the same view. No producer protocol, IPC or speculative/committed cursor change is needed. |

Consequences for the design:

- Membership must be computed from the training shards themselves (the only
  training-side truth) and must exclude every positional field
  (`token_start`, `byte_start`, `byte_end`), so it is order-independent.
- The order intervention is an index over the existing payload: no token bytes
  are duplicated, and the 2 GiB input cap is untouched.
- The committed data state must bind the order identity, and the checkpoint
  loader must compare it before any model/optimizer state is restored (closing
  row 13 for ordered streams).
- M4 must read the order identity from receipts (row 12) and must validate
  the order declaration it is given instead of trusting its labels.
