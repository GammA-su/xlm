Additional facts that shaped the design:

- `TrainingConfig.model_dump` output *is* the envelope config. Adding defaulted
  fields would change every legacy envelope, and `validate_envelope`
  re-resolution would then reject old checkpoints. New fields must be absent
  from legacy resolution.
- The P34 boundary test `test_exact_optimizer_boundary_failures[schedule]` pins
  the legacy post-mutation `apply_lr_to_optimizer` call inside the in-doubt window.
- No group sets `lr_multiplier` today, but `apply_lr_to_optimizer` honors it; a
  plugin optimizer could build groups with distinct `lr` and no multiplier, which
  legacy silently collapses after update 1.
- Probe on the RTX 4090 (torch 2.14.0+cu126, scratch script, no model training):
  defaults are `matmul.allow_tf32=False`, fp32 matmul precision `highest`,
  `allow_bf16_reduced_precision_reduction=True`; `use_deterministic_algorithms(True)`
  does not raise for cuBLAS without `CUBLAS_WORKSPACE_CONFIG`; restricting SDPA to
  `EFFICIENT_ATTENTION` runs causal and boolean-mask calls through
  `aten::_efficient_attention_forward/backward`; restricting to an unavailable
  backend raises `RuntimeError` instead of falling back.

## 3. LR semantics and captured values

`f` is the unchanged warmup/cosine function; `C` is committed targets before an
update; `N` is its actual valid targets after masking and final-budget truncation.

- **Legacy** (`legacy_base_then_postcommit_v1`): update 1 uses the constructed
  base LR. After the CUDA barrier, still inside the in-doubt window, the trainer
  applies `f(C+N)` for the next update. The code path is unchanged.
- **Endpoint** (`target_endpoint_before_update_v1`): `f(C+N)` is derived right
  after `N` is known, before forward/backward. It is installed (times any
  `lr_multiplier`) immediately before `_update_in_doubt = True` and
  `optimizer.step`. Counters, `batcher.commit()` and the LR receipt follow only
  after the barrier.

**Deviation from the prompt's ordering, by design.** The LR is *installed* after
forward/backward and the finite checks, not before them. Neither reads the LR,
and this way every pre-mutation failure leaves group LRs untouched: there is no
LR rollback path to get wrong. The value itself is still derived first.

Captured at `optimizer.step` by wrapping the step and reading every group's `lr`
at call time ([capture_lrs.py](../evidence/P35-M1/capture_lrs.py) to
[lr_capture.json](../evidence/P35-M1/lr_capture.json); tiny model, actual
65,536-target updates, W = 10,000,000, H = 1,000,000,000, base 0.001):

| Case | Update 1 | Update 2 |
|---|---:|---:|
| Legacy, CPU | 0.001 | 6.5536e-06 |
| Endpoint, CPU | **6.5536e-06** | **1.31072e-05** |
| Endpoint, CUDA statistical BF16 | **6.5536e-06** | **1.31072e-05** |
| Endpoint, partial final N = 1,000 | 6.5536e-06 | 6.6536e-06 = f(66,536) |

Each value also equals `schedule.get_lr(counter)` exactly and the decimal
reference within 1e-12 relative. As an independent check, AdamW's first CPU
step moved the largest coordinate by 0.001 (legacy) and 6.5536e-06 (endpoint)
within 2%, as `m_hat/sqrt(v_hat) ≈ sign(g)` predicts.

Boundaries tested (N = 16): warmup crossing, exact warmup endpoint (= base),
exact horizon (= min LR), no warmup (cosine from update 1), cosine region and
final partial update, each equal to `get_lr(C+N)`. Zero-valid updates, under
both policies: no `optimizer.step`, unchanged group LRs, no counter or receipt,
exactly one data `commit()`. Per-group `lr_multiplier` 0.5 gives `[f, 0.5f]`.
A group built with a distinct LR and no multiplier is refused for science-v1
(`endpoint rate is ambiguous`) and runs unchanged under legacy.

## 4. LR receipts and provenance

`TrainingStepMetrics.learning_rate` keeps its historical meaning, the schedule
at the post-update committed count. Under legacy that is the next LR; under the
endpoint policy it equals `lr_used`. New fields: `lr_policy`, `lr_used` (per
group, what `optimizer.step` read), `lr_schedule_counter` (`C+N`, endpoint only)
and `lr_next` (installed next LR under legacy, `None` under endpoint). For
science-v1, `science.json` keeps every committed update as
`[step, committed_before, valid_targets, schedule_counter, lr_used]`, columnar,
bounded at 1,000,000 rows (about 70 B/row; a 1B-target run is about 15k rows).
A receipt is built before the counters and appended only after
`batcher.commit()` clears the in-doubt flag.

## 5. Failure and resume

Injected failures on a science-v1 run after one committed update:

| Stage | Result |
|---|---|
| Pre-step (NaN gradient) | `NonFiniteGradientError`; no in-doubt; LRs, cursor, counters and receipts unchanged; the same update then succeeds with `f(32)`. |
| Optimizer mutates then raises | in doubt; `train_step`, `_save_checkpoint` and `CheckpointManager.save_checkpoint` raise `RecoveryRequiredError`; no new checkpoint directory; no receipt. |
| Post-barrier schedule evaluation | same as the optimizer stage. |
| Counter promotion | same as the optimizer stage. |
| Data commit | same as the optimizer stage. |
| CUDA barrier (`synchronize` raises) | in doubt, cursor unchanged, no receipt, checkpoint refused. |

After each in-doubt case, a fresh trainer reloads the last durable checkpoint,
adopts its receipts and continues with `f(32)`. Exact endpoint resume from
checkpoints after update 1 and after update 2 (whose next update is partial)
reproduces captured LRs, receipts, weights, Adam slots and batcher state
bitwise on CPU. Ordinary resume is refused *before any state is restored* when
the checkpoint's policy differs from the run's: legacy vs science, a changed
`training_seed`, or a changed runtime block. `is_fork` is permitted, and a fork
across policies does not adopt the parent's receipt history.

## 6. Training RNG

`construct_training_components` seeds `init_seed` and builds every component,
exactly as before. Then, for science-v1 fresh runs only, it calls
`reseed_training_rng(training_seed, device)`: Python, NumPy (`seed % 2**32`),
torch CPU, and `torch.cuda.manual_seed_all` on CUDA. It records
`{policy, training_seed, generators, state_digest}` as the train-start receipt.
The attention probe that runs next uses a private generator. CLI resume calls
it with `fresh_training_rng=False`; the queue retry path reseeds at construction
and then restores the checkpoint, so the restore is authoritative. Legacy is
untouched: its post-construction RNG equals seeding `init_seed` and
constructing the same model and objective by hand, and a guard shows the
reseed is never called.

Proofs (CPU unless noted):

- Same init, training seeds 1 and 2: identical initial weights, different
  train-start digests, different weights after one dropout update.
- Init seeds 101 and 211, same training seed: different weights, identical
  train-start receipts.
- An objective constructor that consumes Python, NumPy and torch RNG changes
  the legacy post-construction digest, but not the science-v1 receipt or the
  weights after one dropout update.
- Resume: after save, destroying the trainer and scrambling all RNGs,
  reconstruction without reseed and restore reproduce the Python state, NumPy
  state and torch CPU state. There were zero reseed calls, and the run finishes
  bit-identical to the uninterrupted one.
- CUDA: the restored CUDA generator state equals the saved one, and the next
  dropout update's forward loss matches exactly.
- Direct, queue and resume (CUDA workflow): identical `train_start_rng` and
  receipts.

## 7. Scientific runtime identity

- **Scope.** `ScientificRuntime.scope()` wraps each update. It sets
  deterministic algorithms (error mode, never warn-only), cuDNN
  deterministic/benchmark, `matmul.allow_tf32` and
  `allow_bf16_reduced_precision_reduction`, reads them back, and fails on any
  mismatch. It restricts SDPA (efficient on CUDA, math on CPU) and restores
  every prior value on exit, including on exceptions. Legacy runs get a no-op
  scope, and their worker still sets the historical global flag.
- **Statistical mode** (`statistical_efficient_v1`). The receipt observed
  `aten::_efficient_attention_forward/backward` with deterministic algorithms
  and TF32 off, BF16 probe. Restriction means an unsupported input raises
  instead of silently using another kernel.
- **Strict mode** (`strict_deterministic_v1`). Tested in a fresh CUDA process
  with `CUBLAS_WORKSPACE_CONFIG=:4096:8`:
  - two runs (4 updates each, dropout 0.1, efficient SDPA) gave identical weights;
  - `torch.histc` inside the scope raised the deterministic-implementation error;
  - the flag was `False` again after the scope.

  Strict CUDA without the workspace variable is refused at trainer
  construction. The frozen launcher injects the variable for strict envelopes
  only.
- **Receipt limits.** The receipt is a small attention-operator probe (one
  causal and one boolean-mask call). It is explicitly **not** a whole-model
  determinism certificate.
- **Precision, TF32 and reduction.** `training.precision` (already in
  identity) keeps failing loudly on unsupported combinations. TF32 and BF16
  reduced-precision reduction are now explicit identity fields enforced by the
  scope. `disabled`/`allowed` equal the torch defaults on the P34 path; no
  default changed.
- **`producer_prefetch`.** It was already a resolved `TrainingConfig` field and
  now demonstrably changes the resolved identity. The producer is untouched.
- **Identity test.** Science-v1, legacy LR policy, `training_seed`, strict
  attention, TF32, BF16 reduction, precision, producer and init seed give 9
  distinct resolved digests. Each is idempotent under re-resolution (the
  resume path). A forged science envelope carrying the legacy runtime policy is
  rejected.

## 11. Open risks and questions

1. `training/profile.py`/`profile_worker.py` still build a legacy Trainer, so
   profiling a science-v1 config does not apply its runtime scope. Before the
   contract's strict-mode cost calibration, the profile path should honor
   `training.runtime`.
2. Science-v1 statistical workers no longer set `use_deterministic_algorithms(True)`
   process-wide, as legacy frozen workers do. This is intended (statistical
   mode), but same-seed statistical reruns are not bitwise, and only data
   accounting is claimed equal.
3. The strict-mode cuBLAS check verifies the environment variable, not that
   cuBLAS honored it. In-process domain-API use must set it before the first
   CUDA handle; frozen workers get it at process start.
4. The attention probe is one small shape. Enforcement comes from the per-update
   SDPA restriction, not the probe.
5. A fork across policies starts an empty receipt history. Richer fork
   provenance belongs with the M4 manifest.
6. Periodic checkpoint cadence after resume is still recalculated from the
   resumed count (contract §A); it is untouched here and M3 owns it.
7. `torch.profiler` prints two `USDT … profiler_start/stop` lines to stderr at
   science trainer start. This is cosmetic.
