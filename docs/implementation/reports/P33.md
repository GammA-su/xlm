## Interpretation and rejected experiments

Only the CUDA gradient finite-check / norm-transfer consolidation is retained
as a product change. It transfers one finite predicate per CUDA device and
one vector of per-parameter norms on a single-device model. The norms and
ordered Python arithmetic are identical to the reference. CPU and mixed-device
paths remain supported. Tied weights are still deduplicated for clipping;
finite-element and finite-norm overflow checks remain distinct.

The native RMSNorm experiment is **rejected**. A primitive forward/backward
probe passed, and three updates with the preliminary counter-zero schedule
passed, but the actual release-LR gate failed: maximum observed embedding error
0.0019979905, with 57,508/16,777,216 embedding elements outside the previously
declared `atol=2e-5, rtol=2e-4`. No tolerance was widened. The original RMSNorm
implementation is restored. Records named `native_norm_*`, `final_full_*`,
`final_compute_full_*`, and `prod_combined` contain this rejected prototype;
their names do **not** designate the final retained implementation. The failing
comparison and local diagnostic snapshots are preserved. This is why component
parity and a warmup-zero trajectory are insufficient scientific gates.

The preliminary 8192-target ablation (10 warmup / 50 measured) observed:

|---|---:|---|
| Original scalar gradient checks/clipping | 23,578 | Reference |
| Consolidated gradient transfers | 24,551 | Retain; +4.13%, exact arithmetic |
| Depth-one CPU thread prefetch | 24,490 | Remove; no measured gain |

These are shared-desktop observations, not additive contributions or confidence

not the final advancing-sequence compute baseline.

## Attention, allocation, loss and synchronization audit

The installed wheel selects **memory-efficient SDPA**, confirmed by actual
profiler operators; it does not contain Flash SDPA. At real 50M attention shape
`(B,H,T,D)=(8,8,512,64)`, BF16 forward+backward (10 warmup / 50 measured):

| Available backend | Explicit causal mask ms | `is_causal=True` ms |
|---|---:|---:|
| Math | 4.031 | 2.051 |
| Memory-efficient | 1.032 | 0.763 |
| Flash | NOT RUN: unavailable in wheel | NOT RUN: unavailable in wheel |

Maximum output/gradient errors against math were 0.015625 / 3.815e-6 and
passed the predeclared probe bounds. The production model prepares the causal
and padding/document mask once per forward and shares it across layers. An
unpadded causal shortcut reduced an isolated kernel's cost but did not improve
end-to-end throughput, so document isolation, padding and positions are unchanged.
No third-party attention package was installed.

RoPE already caches sine/cosine tables. Remaining hot-path work includes each
layer's position maximum scalar read, model token min/max checks, objective
valid-count/label-bound checks, and loss scalars. The trainer reads CPU loss-mask
counts before transfers, transfers IDs/labels/masks/positions synchronously, and
constructs the input attention mask on device. CE converts BF16 logits to FP32,
flattens with a view, computes per-token CE and masks/reduces valid targets.
The FP32 cast is substantial at large microbatches (the B64 capacity failure
requested another 4 GiB here); it preserves the existing stable loss definition.
No per-token Python loop is introduced into CE. Loss is scaled by the exact
global valid-target denominator; clipping, scheduler and optimizer run once
per committed optimizer update, including partial final microbatches.

Repeated `.item()` calls are real synchronization sites. Removing the
per-parameter finite/norm transfers is safe and tested; delaying nonfinite loss
checks or committing cursors early is not. No failure guard or metric was
dropped. `optimizer.zero_grad()` already defaults to `set_to_none=True` in this
installed PyTorch; no redundant switch was added. Model forward has many small
RMSNorm/RoPE/elementwise kernels and Python layer dispatches. The native fusion
failed the release gate, so custom kernels were not pursued.

In one instrumented counter-zero full-batch reference update, the profiler saw
800 `aten::item` calls, 684 stream synchronizations, 17 triangular-mask calls
and 32 `arange` operator events. B32 on the retained release path saw 285,
122, 5 and 8 respectively; this comparison combines fewer microbatches and
the retained gradient change. Counts are profiler events, not unique source
sites. Chrome-trace kernel event counts for full updates were 27,999 for original
B8, 28,002 for retained B8 and 8,638 for retained B32. The retained change
reduces host transfers rather than fusing model kernels. Mask/position allocation
kernel time was tiny (tens of microseconds),
so no shape/device cache with additional lifecycle state was added.

CPU profiling identifies the exact per-target trace chain (65,536 digest calls
per full update), JSON serialization and stream-window construction as large
loader costs. mmap payload reads are bounded and already persistent. Profiling
adds substantial overhead, and the watchdog's filesystem inventory can appear
in profile records; cProfile percentages must not be read as uninstrumented
wall-time fractions. Separate event/wall stage measurements establish the
loader delay. A depth-one CPU thread did not improve throughput; its prototype
was removed. A process producer could avoid GIL contention but needs explicit
speculative/committed cursor and resume design. It is deferred to P34.

Training metrics are constructed after optimizer/cursor commit; their scalar
loss and norm inputs have already synchronized. `Trainer.train()` appends the
metrics to an in-memory history and checks interruption/resource limits; it
does not add a per-update disk logger here. Periodic and final durable
checkpoints are measured separately. The throughput window calls the real
`train_step()` and records its metrics, excluding campaign setup/finalization,
fixture construction, resident preparation and checkpoint publication.

`torch.compile`: **NOT RUN**, because Triton is absent and the Windows compiler
is not on PATH; no toolchain installation is authorized. CUDA graphs are also
**NOT RUN**: dynamic partial microbatches, host scalar guards and rollback/resume
state make capture a lifecycle change. Launch overhead is observable, but
forcing graph capture into this path is not justified by the measured data gap.

## Final numerical and subsystem gates

The full-budget frozen reference uses three actual release-LR updates at
65,536 valid targets each, B8, seed 101, the real fixture/loader and original
gradient code. The retained B8 change is **bit exact**: all final parameters,
initial logits retained for comparison, losses, CE metrics, gradient norms,
optimizer steps, learning rates and target counters match. The actual-50M CUDA
test separately compares SHA-256 of **every clipped gradient** before each
optimizer step, every final parameter and committed cursor, also exactly.
Its first applied LR is explicitly asserted to be 0.001. Initial parameter
SHA-256 is
`c0f0f5cf9f2df62dd0553985dfd1585b70ab9fa2c880b99aa8eb28ee48f7ef12`.

**The faster B16 and B32 settings fail the predeclared release-LR parameter
gate against B8.** Observed embedding errors are 0.001989974 and 0.002002771,
with 86,360 and 123,353 elements outside tolerance respectively. Comparisons
stop at the first failed tensor, so these are observed maxima, not an asserted
whole-model maximum. Their losses remain close, but loss closeness does not
override the parameter criterion. The report's 48,834 targets/s / 1.524x B32
result is consequently a **capacity/performance observation, not a certified
drop-in speedup**. No microbatch default is changed, and the threshold is not
relaxed. Earlier counter-zero accumulation comparisons passed a weaker initial
update path; they do not supersede this failure.

The certified 50M recommendation against this frozen B8 reference is therefore
BF16/FP32 masters, **B8**, exact 65,536-target accumulation (nominal 16, actual
17 microbatches on this fixture), existing memory-efficient masked SDPA,
default foreach-selected AdamW, existing set-to-none zeroing, pageable transfer,
no prefetch, no activation checkpointing, no compile and original RMSNorm,
plus the retained gradient transfer consolidation. Selecting a new B16/B32
scientific reference would require a separate contract decision; P33 does not
reinterpret the release's first-step LR or silently relax equivalence.

late NaN/Inf, finite-element norm overflow, mixed-device auxiliary gradients,

## Final bottleneck and next milestone

**DATA-LIMITED, with additional CPU launch/synchronization overhead.** The
50M B8 profile spends about 824 ms preparing an update; resident execution is
substantially faster. B32 spends about 797 ms in the loader out of 1410 ms
total despite much larger GPU kernels. H2D itself is small. This is not evidence
of a saturated compute or hardware memory-bandwidth ceiling. SM occupancy was
not observed. Larger microbatches alleviate launch overhead but do not remove
the trace/accounting delay and fail the frozen B8 numerical gate.

Further general GPU micro-optimization has low value until input overlap is
addressed. A bounded process producer is worthwhile to investigate in P34;
more thread prefetch, mask caching or optimizer toggles are not supported by
a compelling end-to-end gain here. The existing first-update LR behavior also
deserves a separate scientific-contract review before adopting new numerical
kernels or batch settings; it is deliberately preserved in this milestone.

A benchmark JSON status `VERIFIED` means the bounded run completed and recorded
metrics. It does **not** certify that a variant is numerically equivalent; that
decision belongs to the separate comparison/test evidence. A capability skip,
resource abort or rejected candidate is never counted as a pass.

The sampled aggregate artifact guard aborted `eq_checkpoint` with exit 125;
later inventory was 8,724,728,074 bytes against the 8-GiB cap. Completed
diagnostic snapshots were compared, hashed and removed by explicit owned path,
then the corrected named run completed. The cap was not raised. The harness now
reserves estimated snapshot bytes before writing and retains only one initial
logit row, alongside every final parameter. Sampling can still observe a breach
after allocation; this is an application guard rather than an OS quota.

OOM capacity experiments exit their CUDA process with failure JSON. Subsequent
cases run in fresh processes; no corrupted trainer is reused and no batch size
or target count is silently reduced to manufacture a pass. The WDDM OOM error
can print an invalid huge per-process memory sentinel; it is not a resource
measurement. Use the allocator counters, cap and device-total fields instead.

P34 recommendation: first prototype a **bounded producer process** that prepares
the next exact update while CUDA executes the current one, keeping speculative
and committed cursors separate, rollback/restart reproducible and memory capped.
Preserve the per-target trace chain; never replace it with a weaker checksum.
Then design immutable model/optimizer/RNG/sampler CPU snapshots, a bounded
background publisher, explicit in-flight ownership, durable intent and restart
reconciliation for checkpoint tails. Snapshot creation must finish at a valid
optimizer boundary; publication must preserve all existing durability checks.
Neither proposal is authorized as a research campaign or implemented here.
