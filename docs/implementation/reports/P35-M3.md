## 1. Pre-change audit (written before any product edit)

Read from the code at `a3e5546`. Paths are under `src/xlm/`.

| # | Question | Finding |
|---|---|---|
| 1 | Checkpoint trigger | `training/trainer.py::_train_update` step 9: after the commit, the LR receipt and `evaluation.record_crossings`, if `committed_valid_targets >= next_checkpoint_target` the trainer saves `{run_id}_step_{step}_ckpt` and adds `checkpoint_every_valid_targets` to `next_checkpoint_target`. `train()` saves `{run_id}_final` on completion and `{run_id}_interrupted` on a cooperative stop. The queue (`experiments/queue.py::execute_plan_run`) additionally saves `{job}_cancelled`, `{job}_time_limit` and `{job}_final`. |
| 2 | Periodic cadence basis | Configuration-based and **relative**: `training.checkpoint_every_valid_targets` (default 16,000,000). `next_checkpoint_target` starts at `committed + every` when the `Trainer` is constructed and then advances by `every` from the previous *target* (not from the actual count), so an uninterrupted run fires at the first committed boundary at or above each multiple of `every`. There is no named threshold, no event identity and no record of which threshold a checkpoint satisfied. |
| 3 | After resume | Every resume path recomputes the relative cadence from the resumed count: `Trainer(committed_valid_targets=C)` sets `next = C + every` (CLI resume), and the queue retry sets `trainer.next_checkpoint_target = meta.committed + every`. A checkpoint at C = 16,060,928 therefore moves the next checkpoint to 32,060,928 instead of the first boundary ≥ 32,000,000: **cadence drifts by the overshoot** (contract §A "Resume" row, M1 risk 6). |
| 4 | Authoritative checkpoint | No notion exists beyond "the one the operator named". CLI `xlm resume <dir>` uses the given directory. Queue retry scans `<work>/artifacts/checkpoints/{job}_*`, verifies each (`ArtifactStore.verify_artifact`), requires matching `run_id`/`plan_id`, and restores `max((committed, step, is_final))`. |
| 5 | Checkpoint artifact identity | Artifact id = the checkpoint id string, kind `checkpoints`. `ArtifactStore` manifest v2 records per-file SHA-256/size, `production_key`, `content_hash`, `producer_code_hash` (envelope code hash or domain-API source hashes), `dependency_hash`, `resolved_config_hash` (= frozen plan hash) and metadata = `checkpoint_meta.json` fields plus `execution_provenance_hash`. Science-v1 adds checksummed `science.json` (policy, RNG/LR/runtime receipts, M2 evaluation ledger). No model-state digest, data-cursor digest or event identity is in the manifest; the M2 ledger records only the crossing's in-memory `model_state_digest`. |
| 6 | Store / ledger / reconciliation guarantees | `artifacts/store.py`: payload fsync → manifest → `_COMPLETED`, private UUID staging under `<root>/.staging`, atomic rename, **never replaces** an existing destination (identical request returns it; different payload/provenance raises `ArtifactConflictError`). `artifacts/ledger.py` (`RunLedger`, SQLite): `record_artifact` upsert; `rebuild_from_filesystem` records only fully verified store artifacts, idempotently and bounded; `audit_ledger_references` marks missing/corrupt references `unverifiable`; **rows are never deleted**. The store is authoritative; the ledger is a catalog. |
| 7 | Cleanup / retention | **None for checkpoints or any published artifact.** The only deletions are the store's own private staging directory (`store.py`), snapshot capture's private temp (`experiments/snapshot.py`) and the operator release path's temporary file. "retention" in `reports/` is dataset-side reporting, unrelated. Every checkpoint of a run is kept forever. |
| 8 | Protection of referenced artifacts | Not needed so far because nothing deletes. Lineage is declared (`input_artifact_ids`, optional `input_manifest_hashes`), fork parents are recorded in `checkpoint_meta.json` (`parent_checkpoint_id`), and M2 attempts record model-state digests, but no component checks references before a deletion. |
| 9 | Staging/temp effect on peak disk | A save serializes every file into a `tempfile.TemporaryDirectory()` (in frozen workers `TMP` is the worker directory inside the job work dir), then `publish_artifact` copies the bytes into `<root>/.staging/<id>_<uuid>` and renames. Peak during one save = retained checkpoints + **2 × new payload** (+ manifest). `_save_tensor` guards each tensor with `(cap − published)//2 − staged − 2 MiB`, i.e. it already assumes a 2× transient. `_published_bytes` only grows. The launcher samples owned work-dir bytes every second against `max_owned_disk_bytes` (ticket `max_new_disk_gib`, default 2 GiB) and kills the worker on excess. |
| 10 | Planning command and plan representation | `xlm experiment plan DRAFT [--output] [--snapshot-dir] [--profile] [--json] [--smoke]` → `experiments/plans.py::resolve_experiment_plan` → `ExecutablePlan` (JSON). Nulls become `PlanBlocker`s (`missing_*`, `unresolved_*`, `cost_unestimated`, `storage_exceeds_cap`, `tier_not_executable`); only a blocker-free plan is frozen (`freeze_execution`: captured snapshot + `make_envelope`, `plan_version` 2, `plan_hash = identity_digest(identity_payload())`). `--smoke` is the C13 path. There is no `validate` verb and no pilot-specific preflight. |
| 11 | Operator authorization | `xlm experiment authorize --plan-hash H --max-targets N --approver A --ticket-id T [--max-seconds S] [--max-disk-gib G] -o ticket.json` issues an `AuthorizationTicket` bound to one plan hash. `xlm experiment submit plan.json --ticket ticket.json --device cuda` refuses blockers, re-verifies plan identity and envelope, and checks the ticket covers targets, `budget_max_seconds`, `storage_estimate_gib` and GPU processes; without a ticket only the C13 smoke caps apply. Admission (`admission.json`) is bound to the ledger authorization token and re-checked by `queue run`. |
| 12 | Storage paths and resource ceilings | One root: `XLM_HOME` (`core/paths.py`). Queue jobs write `<XLM_HOME>/runs/<job>/{plan.json,admission.json,worker-N/}` and their store at `<XLM_HOME>/runs/<job>/artifacts`; the worker's `TMP/TEMP` is its `worker-N` directory. Ceilings: `resources.max_new_disk_gib`, `resources.max_gpu_processes`, `training.budget.max_train_seconds`, ticket limits, launcher output cap 16 MiB and entry cap 10,000. RSS is sampled, not limited; GPU memory is neither declared nor limited. No data/temp/output roots are declared or checked. |
| 13 | Total wall clock across resume | **Not supported.** `execute_plan_run` restarts its clock per attempt (`budget_max_seconds or 600`), the launcher kills at `max_train_seconds + 120` per worker, and nothing persists consumed time. A resumed attempt receives the full allowance again. |
| 14 | Evaluation events vs checkpoints | `record_crossings` runs inside `_train_update` right after commit and **before** step 9's periodic checkpoint; `run_pending` runs after the update returns (`train_step`). A checkpoint at a crossing boundary therefore owes that boundary's events (`due`). Events are not linked to checkpoint ids; the relation exists only through equal committed counts and the in-memory model digest. |
| 15 | `score_checkpoint_validation` | Verifies the checkpoint artifact, hashes `model.pt` before and after loading, loads model and tokenizer (explicit path or co-located), verifies the pinned LM inventory against the tokenizer fingerprint, builds `LMValidationEvaluator`, computes `model_state_digest` and scores. It returns `model_state {checkpoint_v1, id, manifest sha, weights sha, state digest}`, evaluator identity, status, metrics, coverage. It does **not** compare against an expected event or digest, publish an attempt, touch any ledger, apply the science runtime scope, guard the caller's RNG (model construction consumes it), or support benchmark tiers. M2 verified its digest and metrics equal the in-memory receipt on CPU. |

Additional facts that shaped the design:

- The M2 ledger is loaded strictly: `EvaluationLedger.from_dict` refuses a
  different `canonical_rule`/`retry_policy`, so M2 constants cannot change
  without breaking M2 resume. Any rescore route must be additive.
- `EventRecord.lineage_attempts()` selects attempts by exact
  `computation_identity`, which includes `model_state.kind =
  in_memory_replica_v1`, the device and the runtime. A checkpoint-sourced
  attempt needs an explicit, additive lineage binding to be canonical.
- `ExecutablePlan.to_dict()` feeds the plan hash; adding a dataclass field
  would change every persisted plan's identity. Pilot data must live in the
  resolved configuration (which the envelope and hash already cover) or in a
  sidecar bound to the plan hash.
- `resolve_execution_config` refuses unknown top-level keys and fills
  `max_train_seconds = 600` when null, so a 32M pilot must declare its
  per-attempt training limit explicitly; that limit is not the total deadline.
- `resolve_training_input` caps aggregate frozen shard inputs at 2 GiB and
  requires every document record to be `split == "train"`; the latter is the
  existing training-membership firewall.
- No cold-read instrumentation exists anywhere in `src/xlm`.
- `suites.partition_grouped_items` already defines the deterministic
  HellaSwag/PIQA group halves, but declared manifests carry no group keys, so
  membership cannot be checked without a user-supplied item→group mapping.
