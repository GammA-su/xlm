Additional facts that shaped the design:

- The M2 ledger is loaded strictly: `EvaluationLedger.from_dict` refuses a
  different `canonical_rule`/`retry_policy`, so M2 constants cannot change
  without breaking M2 resume. Any rescore route must be additive.
- `EventRecord.lineage_attempts()` selects attempts by exact
  `computation_identity`, which includes `model_state.kind =
  in_memory_replica_v1`, the device and the runtime. A checkpoint-sourced
  attempt needs an explicit, additive lineage binding to be canonical.
- `ExecutablePlan.to_dict()` feeds the plan hash; adding a dataclass field
  would change every persisted plan's identity. Pilot data must live in the
  resolved configuration (which the envelope and hash already cover) or in a
  sidecar bound to the plan hash.
- `resolve_execution_config` refuses unknown top-level keys and fills
  `max_train_seconds = 600` when null, so a 32M pilot must declare its
  per-attempt training limit explicitly; that limit is not the total deadline.
- `resolve_training_input` caps aggregate frozen shard inputs at 2 GiB and
  requires every document record to be `split == "train"`; the latter is the
  existing training-membership firewall.
- No cold-read instrumentation exists anywhere in `src/xlm`.
- `suites.partition_grouped_items` already defines the deterministic
  HellaSwag/PIQA group halves, but declared manifests carry no group keys, so

## 3. Boundary planner, thresholds, overshoot and the final partial update

- **Absolute thresholds, first crossing.** A checkpoint threshold `T` is due at
  the first committed boundary with `C >= T`, exactly like an evaluation. No
  update is ever split: checkpoint and evaluation logic run only after an
  update has committed.
- **Pilot arithmetic** (`update_arithmetic(32_000_000, 65_536)`, tested): 488
  full updates + one masked update of 18,432 = 32,000,000 targets, 489 updates.
- **Pilot checkpoint projection** (tested):

  | Threshold | Actual C | Update |
  |---:|---:|---:|
  | 0 | 0 | 0 |
  | 8,000,000 | 8,060,928 | 123 |
  | 16,000,000 | 16,056,320 | 245 |
  | 32,000,000 | 32,000,000 | 489 |

  Each record stores `planned_thresholds` and `actual_committed_targets`; the
  8M state is never called "8M" without both.
- **Overshoot**, trainer-verified with batch 16: threshold 8 fires at C=16 and
  records planned 8 / actual 16; threshold 32 is exact at C=32. Updates stay
  16/16/16.
- **Multiple thresholds** crossed by one update publish **one** checkpoint
  whose record lists every event (4, 8, 12 at C=16).
- **Final partial**: budget 40, batch 16 → updates 16/16/8. The endpoint
  checkpoint fires once at C=40. `train()`'s final state reuses it, and no
  `_final` duplicate is published.
- **Zero-valid work** fires nothing.
- **Order at one boundary**: evaluation crossings recorded → checkpoint
  published (its `science.json` shows the boundary's evaluation as `due` and its
  own record as `publishing`) → evaluations scored. The M2 crash semantics are
  preserved: a crash after publication but before scoring leaves an exactly
  rescorable state.
- **Deduplication**: a checkpoint milestone and an evaluation at the same C
  share one checkpoint artifact, but keep separate checkpoint receipts
  (`checkpoint_events`) and evaluation attempt receipts (`evaluations`).

## 4. Checkpoint event identity

Every science-v1 checkpoint record binds:

- run (`run_id`, `plan_id`, run key, `execution_hash`);
- per-event `event_identity` (SHA-256 of run key, checkpoint-plan digest and
  event id), planned threshold and role;
- `actual_committed_targets`, `processed_valid_targets` and `step`;
- `model_state_digest` (the M2 `state_dict` digest) and `data_cursor_digest`
  (committed batcher state);
- `science_identity` (policy identity plus checkpoint- and evaluation-plan
  digests);
- ArtifactStore id `{run}_ckpt-t{T}-a{attempt}` and `creation_attempt`;
- the verified `manifest_sha256`, `content_hash` and payload bytes;
- status `publishing/published/failed/retired`.

`identity_digest` is recomputed on load, so a tampered record is refused.
Terminal states use `{run}_ckpt-{reason}-c{C}-a{n}`. Legacy runs keep
`{run}_{reason}` and `{run}_step_{n}_ckpt`.

## 5. Resume without drift or duplicates

- The ledger is restored from the checkpoint and never recomputed from the
  resumed count. Test (batch 12, recovery 16/32): the uninterrupted run
  publishes at C = 24 and C = 36. A resume from the C=24 checkpoint publishes
  the next checkpoint at C=36, not at 24 + 16 = 40 as the historical relative
  cadence still does. Every artifact exists once.
- **Already completed** milestones are handled and never republished.
- **Crossed, but publication failed**: the record is FAILED with a failure
  receipt, and training stops (`CheckpointPublicationError`). A fresh process
  from the last good state publishes attempt 2; attempt 1's failure shows in
  the ledger history.
- **Died before crossing**: normal replay crosses it later.
- **Died after the durable rename, before finalization**: replaying from an
  earlier checkpoint *adopts* the existing artifact. This requires run, plan,
  C, step, data-cursor digest and a `model.pt` digest all identical, and
  nothing is republished. Resuming from that checkpoint itself settles its own
  `publishing` record (verified artifact). A divergent replay (different
  weights) publishes attempt 2 and records attempt 1 as a lost lineage.
- **Plan changes**: a changed checkpoint plan, or checkpoint-cadence presence,
  refuses ordinary resume before any state is restored. A fork re-originates
  the plan and protects the parent checkpoint.
- **Queue retry**: the trainer's absolute cadence is not re-anchored
  (`next_checkpoint_target` is only reset for legacy runs).

## 6. Retention

`latest_two_recovery_plus_pinned_v1`, decided over **verified records**, never
filenames:

- **kept**: pinned milestones, the two newest recovery states, the last good
  state, protected references (declared or fork parent), and every state an
  unresolved evaluation event may need (by model-state digest);
- **retirable**: older recovery states and lost-lineage publications owned by
  this run (the checkpoint metadata must name this run and plan; a foreign
  run's checkpoint in the same store is never a candidate).

Evidence, from tests:

- **Latest two**: recovery 8…40 plus milestones 0 and 48 at batch 8 leave
  exactly t0, t32, t40 and t48. t8, t16 and t24 are `retired`, with reason
  `rolling_recovery_beyond_latest_two` and the replacement that preceded
  each retirement.
- **Pinned**: milestones are always kept. A declared reference or fork parent
  is kept with reason `reference:…`.
- **Evaluation dependency**: a failed `quick_lm@16` keeps t16 beyond the
  latest two, with reason `evaluation_dependency:quick_lm@16`. The toy flow
  shows the release: t4096 was kept while `quick_lm@4096` was unresolved and
  retired after its exact rescore completed.
- **Publication failure**: t24's publication fails with a device error; t8,
  which that publication would have displaced, is still present and verifies.
- **Order**: every `retire_artifact` call happens after the replacement was
  published and verified; the test asserts this at each call.
- **Store safety**: a changed manifest hash or missing target is refused and
  the artifact stays intact. An interrupted retirement leaves only a hidden
  tombstone, which ledger rebuilds ignore and `purge_tombstones` removes. The
  run ledger keeps `retired` rows, and audits count them as retired.
- **After resume**: a record retired after its checkpoint was serialized is
  re-synced from the run ledger as `retired`.

## 7. Capacity and storage roots

**Peak model** (`capacity_plan`). For each planned publication it takes the
retained bytes (pinned milestones, planned recovery, plus two unplanned
recovery states: an upper bound) plus **2 × checkpoint size**, one copy in the
serialization directory and one in store staging. It then adds code-bound
bytes:

- checkpoint receipts (4 MiB each);
- the launcher's 16 MiB log spool;
- job JSON (8 MiB each);

and operator-declared evaluation evidence, cache bytes and safety margin. The
checkpoint size must be *measured*: the verified size of a real checkpoint
artifact with matching model config, precision and optimizer state, or the
measured profile's `checkpoint_gib`. An unresolved size blocks. For the pilot
with a size P, the peak before the 32M publication is 5P retained + 2P
transient = 7P (tested with P = 600 MB: fits the 8 GiB new-output limit;
P = 2 GiB is blocked).

**Checks**:

- the peak ≤ the §W new-output limit and ≤ `resources.max_new_disk_gib`;
- free space (`shutil.disk_usage`) on the checkpoint root ≥ peak + margin, and
  on the output root ≥ snapshot + plan/review + margin.

`validate` repeats the free-space check, and the queue repeats it before
leasing a GPU. The plan's `storage_estimate_gib` is the measured peak, so the
operator ticket and the queue's runtime disk cap cover exactly it.

**Roots**: data, checkpoint, temp, evaluation-input(s) and output must be
explicit, absolute, existing plain directories (no symlink or junction), with
no drive or machine hard-coded. Containment is checked on resolved paths, so
`..` traversal is caught (tested):

- shard dirs, exposure plan, tokenizer → data root;
- inventory manifests and document files, benchmark inputs and data files,
  group assignments → evaluation roots;
- plan, review and snapshot → output root;
- the size-source checkpoint → data or checkpoint root.

The existing queue writes a job's store *and* its worker scratch/staging
under `XLM_HOME/runs/<job>`. That path must lie inside both the checkpoint
root and the temp root, otherwise the plan is blocked with
`checkpoint_root_not_honored` or `temp_root_not_honored` rather than
pretending to honor a separate temp volume. A shared checkpoint/temp volume
(`st_dev`) is reported as a warning.

## 8. Rescoring M2 events from retained checkpoints

**Architecture** (§J/§K/§L of the prompt):

1. `locate_exact_checkpoint` finds the record with the event's model-state
   digest, C and step, still published and present (`checkpoint_missing` /
   `checkpoint_not_retained` otherwise). There is **no fallback** to another
   checkpoint.
2. `rescore_event` checks, before publishing anything:
   - the event was crossed and is not complete (unless a deliberate rerun);
   - the tier is an LM tier;
   - `planned_computation(tier, digest, evaluator digest, device, runtime)`
     reproduces the crossing's `computation_identity`, which binds device and
     runtime;
   - the checkpoint verifies, and its run/plan, C and step match;
   - the **stored `model.pt` hashes to the event's digest**;
   - the rebuilt evaluator's identity digest equals the planned one: same
     tokenizer, inventory, scoring policy and scorer source, with a field-level
     diff message.
3. It publishes attempt n+1 (`started`, `outcome`) with its own computation
   identity (`checkpoint_v1` source) and `lineage_identity` = the crossing's
   computation. It scores through `score_checkpoint_validation` with the
   expected digests and runtime scope, so the model load cannot drift.
4. `first_complete_attempt_v1` is unchanged, and lineage now includes the
   verified rescore attempts.

**Success** (CPU test and CUDA toy flow): `quick_lm@16` attempt 1 FAILED at
its live boundary; training continued to C=48; at the budget attempt 2
completed from `m2_run_ckpt-t16-a001`. The attempts read
`[(1, failed), (2, complete)]`, canonical is attempt 2, and completeness is
true. Its metrics are **identical** to an uninterrupted run's live score of the
same state. The training RNG digest and all guarded training state are
unchanged by recovery. A deliberate rerun of a complete event adds attempt 2
and keeps attempt 1 canonical.

**Negative cases**, each refused with no attempt published:

- `checkpoint_counters_mismatch`: the t0 or t48 checkpoint;
- `checkpoint_state_mismatch`: same C/step, different weights (a forged
  verified checkpoint at C=16, step 1, other init seed);
- `evaluator_mismatch`: another tokenizer, another inventory (diff names
  `inputs`), or a different stride (diff names `scoring_policy`);
- `computation_mismatch`: another runtime;
- `checkpoint_missing`: no checkpoint planned at C=32; the latest checkpoint
  is not used;
- `checkpoint_not_retained`;
- `tier_not_rescorable`: the search benchmark, whose checkpoint then stays
  retained with an explicit reason.

## 10. Cold data, total deadline, authorization, launch commands

**Cold data (§W)**: the frozen exposure plan's blocks over the whole budget are
checked for at least two source transitions and a first visit of every
component. Covered → VERIFIED. A layout that lacks coverage reports NOT_RUN
with the warning "plan a separate bounded storage diagnostic" and **does not
change quotas**, as §W directs. Runtime cold-open evidence is **not
instrumented** in M3: the plan records `not_instrumented_report_not_run`, and
the pilot must report it NOT RUN unless measured. No agent-made "cold receipt"
is accepted or produced.

**60-minute total deadline**: `resources.total_wall_seconds = 3600` is bound in
the plan hash and enforced by the queue's outer boundary, not by
`max_train_seconds`. `<job>/wall_allowance.json` persists the plan hash, total,
consumed seconds and every attempt. The runner updates it about once a second
during the worker, so a crashed runner under-records ≤ ~1 s; its attempt is
marked `interrupted_runner_lost`. A resumed attempt's kill limit is the
remaining allowance (tested: 3,600 → 900 consumed → the next attempt gets
2,700, never 3,600). Expiry leaves the job `FAILED` with
`completion: INCOMPLETE`, never success. A requeued job with a spent allowance
is refused before launch. A real frozen CUDA worker was killed at a 4 s
allowance with reason `total wall allowance exhausted` and recorded INCOMPLETE.

**Authorization boundary**: planning and validation never authorize.
EXECUTABLE requires the existing `xlm experiment authorize` ticket for the
concrete hash; no new flag was invented. `submit` still refuses blockers and
checks the ticket, and the queue re-checks admission.

**Commands**: a RESOLVED review renders `$env:XLM_HOME = '<checkpoint root>'`

## 14. Risks and open questions

1. **2 GiB aggregate shard-input cap.** `training/inputs.py` refuses frozen
   mixtures whose shard files exceed 2 GiB in total (per shard also 2 GiB).
   Real mix01 shards for 12 sources may exceed it. The pilot would then be
   BLOCKED at resolution. The cap is pre-existing P34 engineering; revisit it
   deliberately, not in M3.
2. **Events at boundaries without a planned checkpoint cannot be rescored.**
   In the pilot this is `quick_lm@1M` and `quick_lm@4M`. If they fail, the
   pilot stays evaluation-incomplete. Adding checkpoints there would change the
   §W cadence; that decision is the user's.
3. **Search-benchmark events have no verified checkpoint route.** A failed one
   stays incomplete, and its checkpoint is retained with an explicit reason
   until resolved.
4. **The endpoint checkpoint owes its own endpoint evaluations** (by design).
   Completeness is proven by the immutable attempts, reconciled by
   `load_run_evaluation_state` or an at-budget resume, not by that checkpoint's
   `science.json`.
5. **Search item cap interpretation.** §W's "100 items/task" is enforced per
   logical task (all BLiMP subdatasets together). If the user means per BLiMP
   subdataset, that is a contract clarification.
6. **Resume paths.** A worker *exception* is terminal `FAILED`, as before.
   Queue resume covers lost runners/processes (`--max-retries 1`). The §W
   16M-resume check is done by interrupting the runner. The CLI `xlm resume`
   keeps its 200k smoke cap.
7. **Wall-allowance accounting granularity.** Consumption is persisted about
   once a second, so a crashed runner can under-record about a second. Time
   between runner death and the next `queue run` is not charged, since no work
   happens then.
8. **Declared resource caps.** The GPU cap uses
   `torch.cuda.set_per_process_memory_fraction` (allocator cap) plus a
   free-memory headroom check at worker start; it is not a hard driver limit.
   RSS is enforced at the launcher's ~0.1 s sampling.
9. **Superseded lost-lineage checkpoints are retirable.** They are verified
   and run-owned, and are never retired while a protected reference or
   evaluation dependency names them.
10. **Retention log growth.** `science.json` carries the retention log and
    records (bounded at 4,096 each). A 1B run has about 20 publications.
11. **Scientific choices §W leaves to the user.** The scoring policy, TF32/BF16
    reduction flags, NVMe roots and safety margin are required inputs, never
    defaulted.

### 17.8 Real-pilot readiness

**2 GiB shard-input cap** (`src/xlm/training/inputs.py`; not altered).

- **Per shard** (`_shard`): the running total of `shard_manifest.json`,
  `manifest.json`, `tokens.bin`, `offsets.jsonl` and `shard_counters.json`
  must stay ≤ 2 GiB. Any JSON file must be ≤ 8 MiB. Error: `frozen shard
  input exceeds byte limit`.
- **Aggregate** (`resolve_training_input`, mixture branch): the sum over all
  components of `tokens.bin`, `offsets.jsonl`, `shard_manifest.json` and
  `shard_counters.json` must stay ≤ 2 GiB. Error: `aggregate frozen shard
  inputs exceed 2 GiB`. Separately, each `offsets.jsonl` line must be ≤ 8 MiB.
- **Origin:** baseline `0a8ff65` (2026-09-20, D04/D05 snapshot). It predates
  P35 and M3 did not touch it.
- **What it protects.** Every resolution runs a full SHA-256 of each
  `tokens.bin` and `offsets.jsonl`, plus a line-by-line index scan. That
  happens in:
  - `experiments/execution.py::resolve_execution_config`: plan freeze,
    submit/validate and worker envelope validation;
  - `training/components.py`: every worker start and resume;
  - the pilot preflight.

  The cap bounds that input I/O and time (AGENTS.md: bounded work and byte
  limits). Nothing copies shards.
- **Nature of the cap:** an engineering/smoke-era resource bound, **not a
  scientific constraint**. The contract (§G/§W) defines no input-size cap; the
  8 GiB §W limit is about new output.
- **Arithmetic.**
  - At vocab 32,768, tokens are uint16 (2 bytes each), so 2 GiB is at most
    about 1.07 B tokens across all 12 shards.
  - `offsets.jsonl` counts toward the cap as well. It can exceed `tokens.bin`
    when per-token byte spans are embedded.
  - The pilot consumes only 32 M targets (~64 MB of `tokens.bin`), but the cap
    applies to the whole prepared shards.
- **M3 integration: NOT BLOCKED.**
- **Real pilot readiness: POTENTIAL BLOCKER, pending real artifact sizes.**
  The real mix01 artifacts do not exist here; no claim is made that they
  exceed the cap.
- **Future action if they exceed it.** Planning reports BLOCKED with
  `execution_resolution: ValueError: aggregate frozen shard inputs exceed 2 GiB`
  (`run_preflight` catches every resolution failure) and writes no plan. When
  resolution succeeds, the review's `data` section records
  `input_shard_bytes`, so the real size is visible before authorization. If
  the cap is exceeded, either:
  - make a deliberate, separately reviewed change that turns the bound into a
    declared, plan-hash-bound input limit with measured resolution cost; or
  - have the user decide to prepare pilot-scale shards, which is a new data
    identity.

  Do not silently raise the constant.
