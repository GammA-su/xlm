## 3. Implemented Architecture

### 3.1 Extended token shards (`src/xlm/data/tokens.py`)

The prompt forbids a second dataset format, so the existing P02 shard was **extended
in place** rather than replaced. Each offset record now additionally carries
`lineage_id`, `split_group`, `byte_start`/`byte_end`, `valid_targets`, and
`bos_positions`/`eos_positions` structural markers. Aggregate counters
(`valid_targets`, `eos_tokens`, `content_tokens`, `canonical_bytes`) are written to a
`shard_counters.json` sidecar rather than into `TokenShardManifest`, so extending
them never mutates a frozen contract schema.

Reading gained `mmap_tokens()`, `read_tokens_mmap()` and `iter_document_offsets()`.
All three P02/P05 shard tests still pass unchanged.

### 3.2 Mixture recipes (`sampling/mixture.py`)

Weights are shares of **valid target tokens**. A recipe whose weights do not sum to
one is rejected — there is no renormalization path in the code to take. A named
source with no shard, or with zero valid targets, is an error rather than a
redistribution. `ExhaustionPolicy` and `PackingPolicy` are part of `identity()`, so
the scheduling policy is in the regime hash as C07 requires.

### 3.3 Exposure plans (`sampling/plan.py`)

Plans hold **projections and range descriptors**, never positions. A 10⁹-token budget
produces the same size plan as a 10³-token one; blocks come from
`iter_exposure_blocks`, a generator. Repetition risk, epochs required, unique
availability and projected storage are computed at plan time, so a shortfall is
visible before a run rather than discovered from a loss curve.

### 3.4 Scheduler and packers (`sampling/scheduler.py`, `sampling/packing.py`)

`QuotaScheduler` selects by largest deficit with a deterministic tie-break, tracks
per-source unique versus repeated exposure, and reports target shares, content shares
and their `structural_gap` — the difference EOS makes to a source's share.

`CausalStreamPacker` is the C07 baseline (one segment, continuous positions,
cross-document attention). `IsolatedDocumentPacker` gives each document its own
segment, resets positions per document, and masks any target crossing a boundary.
The two are distinct policies; `PackingPolicy` refuses the contradictory combination
of isolated packing with cross-document attention enabled.

### 3.5 Mixture batcher (`sampling/stream.py`)

Implements the same protocol as the single-source `TrainingBatcher`. Committed state
is separate from speculative state, so a prefetched step that is rolled back cannot
skip committed examples. Resume refuses a checkpoint written under a different
mixture identity — a changed mixture is a new data lineage, not a resumable run.

`emit_tensors=False` by default keeps the data layer torch-free; the trainer path
enables it and torch is imported lazily inside the conversion.

### 3.6 Trainer connection

`TrainingBatcher` and `MixtureBatcher` now both satisfy a new `BatcherProtocol` in
`training/data.py`; `Trainer` and `CheckpointManager` are typed against the protocol.
The real `Trainer` drives the mixture loader with **no other changes**.

### 3.7 CLI

`xlm data tokenize`, and `xlm mixture validate | plan | inspect | preview`.

## 5. Defects Found and Fixed During Implementation

Three real bugs, each caught by a test rather than by inspection:

1. **`memoryview` slice blocked mmap close.** `read_tokens_mmap` sliced the map into
   a local `memoryview`, which keeps an exported pointer, so the map could not close
   (`BufferError`, then a Windows file lock). Replaced with `struct.unpack_from`,
   which reads through the map without creating a slice.
2. **Epoch advance missed the carry case.** The exhaustion guard only fired when
   there was no carried context token, so a source at its end *with* a carry produced
   a one-token window and raised a confusing stream error instead of advancing the
   epoch. The guard now accounts for the carry: one more token suffices with a carry,
   two without.
3. **Lineage grouping vs. duplicate detection** (carried over from P10's design) was
   re-verified here: shards record `lineage_id` without it affecting exposure.

## 8. Honest Scope Statements

- **Fixture scale only.** Every number above comes from authored synthetic corpora of
  a few thousand tokens. Nothing here is a throughput measurement, and no
  production-scale corpus was tokenized or trained on.
- **Share drift is granularity-bounded, and the tests say so.** The configured 2%
  steady-state bound is not reachable on a 256-target run where one 32-token window
  is 12.5% of the budget. `test_share_drift_converges_as_the_run_lengthens` asserts
  the granularity relationship and that drift tightens with budget, rather than
  asserting a bound the arithmetic cannot meet at that scale. The trainer test uses
  the same granularity-derived bound explicitly.
- **Bounded-memory claims are structural, not benchmarked.** Reads go through
  `mmap` and offsets stream; plans are range descriptors and blocks are generated.
  Peak RSS under a large corpus was not measured, so no memory figure is claimed.
- **`ESTIMATED_BYTES_PER_TOKEN` is no longer used for these counts.** Availability
  here is exact: valid-target counts come from the shards themselves, which is why
  the plan notes label them an exact interval count rather than a sketch.
- **Multiworker prefetch is not implemented.** The committed-versus-speculative
  boundary that a worker pool would need is implemented and tested (rollback replay,
  cross-mixture refusal, microbatch-grouping independence), but no worker pool exists
  yet. The acceptance item "worker-count/order tests" is covered as
  *partition/microbatch-count independence*, which is what this single-process loader
  can honestly demonstrate.
- **Matched exposure plans are planning-side only.** `compile_matched_plan` and
  `xlm mixture matched-plan` produce matched-canonical-byte and matched-document
  plans that pin raw-text exposure and derive the token budget. Nothing forces a
  training run to consume that derived budget yet; binding a matched plan to a run
  plan belongs with the comparison track (P16–P17). The plans are deterministic and
  identity-bound, and the derived token budget is labelled a projection.
