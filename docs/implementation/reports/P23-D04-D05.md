## 3. What was implemented

### 3.1 D04 — explicit development inputs, real task definitions

`src/xlm/evaluation/inputs.py` *(new, 812 lines)* — versioned evaluation-input
manifest. Each selection declares dataset repository, immutable revision,
configuration, the official split the records were selected from, explicit item
IDs and the field carrying them, BLiMP subdataset membership, artifact path with
byte digest and size, record-schema and adapter versions, and an optional
acquisition-receipt reference. `verify_evaluation_inputs` checks, all fatal:

1. tier admissibility — a developer manifest can never resolve `final`;
2. the split firewall, **derived from `resolve_suite`** rather than restated, so
   it cannot drift from the evaluation policy it enforces;
3. artifact existence, size and SHA-256 (same-length corruption is rejected);
4. exact membership — declared IDs == IDs present, no duplicates, no extras;
5. required BLiMP subdataset cover;
6. agreement with the installed harness version.

No network, no provider cache, and **no code named by a manifest is ever
loaded** (`task_definition_source` is pinned to `pinned_installed_harness`).

`src/xlm/evaluation/harness.py` — `resolve_official_task_config` and
`bind_verified_inputs_to_tasks`. This is the core repair. The old wrapper read
the task YAML as text and copied it, which silently loses `include:` (every
BLiMP subdataset inherits `_template_yaml`) and `!function` (HellaSwag's
`process_docs` lives beside its YAML). The new path uses the harness's own
loader to resolve the definition fully, then rewrites **only** loader keys
(`dataset_path`, `dataset_name`, `dataset_kwargs`, and all four split fields,
each set explicitly so no upstream default can be selected by omission). It then
*asserts* that every behavioural key is the identical object from the official
config, and refuses otherwise. Unsupported output types and any non-zero
`num_fewshot` fail loudly instead of being approximated.

Bound tasks are named `xlmdev_<leaf>`, so a result row can never be mistaken for
an official benchmark run in a log, a cache or a report.

`src/xlm/cli/eval_cmd.py` — `--inputs <manifest>` and `--verify-inputs-only`.
No new command group; `cli/main.py` is untouched.

`scripts/build_eval_inputs.py` — thin operator wrapper; all construction and
verification logic lives in `xlm.evaluation.inputs`.

### 3.2 D05 — expected population, coverage, eligibility

`src/xlm/evaluation/coverage.py` *(new, 479 lines)* — the expected population is
frozen from the manifest **before the harness is asked for anything**.
`reconcile_coverage` then compares it against returned items matched on
namespaced declared identities, tracking expected/scored/missing/unexpected/
duplicate/failed IDs, required-versus-observed BLiMP subdatasets, runtime limit
and interruption. Three states exist: `declared`, `undeclared` (no manifest —
expected counts stay zero rather than being copied from observations), and
`legacy_unverified`.

`compute_four_task_index` gained a `coverage` gate. **The formula, chance
references, denominators and four-task weighting are unchanged**; coverage only
decides whether the computed index may be published.

Item identity now survives execution: `items_from_harness_samples` reads the
declared id from the returned document and **raises** if preprocessing dropped
it. The positional `doc_id` is retained but is never the identity.

D05-0 is fixed by `resolve_metric`, which resolves the configured metric against
the installed result shape: exact key beats suffixed key, `0.0` is a score (not
a missing metric, so membership is tested rather than truthiness), and multiple
filters raise rather than having one picked arbitrarily.

Raw-likelihood identity is separated from aggregate identity. The manifest hashes
prompt-bearing content and gold labels separately, so a relabelling leaves the
raw identity intact and invalidates the aggregate. Cache reuse of stored scores
requires raw identity, aggregate identity **and** the full recorded identity to
match; anything less is `raw_only`, and the suite recomputes.

> **Deliberate non-optimisation, stated plainly:** reusing cached likelihoods to
> skip re-running the model on a `raw_only` hit is *not implemented*. The
> identities are separated and invalidate correctly; the saving is left unclaimed
> rather than faked. The run records a note when this happens.

## 6. Supported and unsupported

### Supported

* Multiple-choice conditional-likelihood tasks (`arc_easy`, `hellaswag`, `piqa`,
  BLiMP subdatasets) bound to verified local JSON/JSONL artifacts in the
  **official record schema**, at the search and confirmation tiers.
* A declared scope narrower than four tasks, complete within itself and labelled
  as such.
* Authored fixture scopes, complete within themselves, permanently ineligible as
  research or promotion evidence.

### Unsupported — fails loudly, not approximated

* Non-multiple-choice output types (`generate_until`, etc.).
* Any task whose resolved config declares `num_fewshot != 0`.
* Records not in the official schema — the official `process_docs` and
  `doc_to_*` expressions read official field names, so a differently shaped
  local extract is refused by the harness rather than silently reinterpreted.
* The final tier from the developer CLI, under any manifest.

### Operator-side requirement (documented, not solved here)

A provider that cannot supply a **split-scoped** representation without pulling
protected data into the development environment leaves that route blocked. This
was not worked around by downloading everything and filtering afterwards. The
operator performs the selection and extraction under their own transfer and
licensing authority; this stage turns the resulting files into a frozen,
verifiable declaration.

Records whose official schema has no intrinsic id (HellaSwag, PIQA, BLiMP) must
carry an explicit `xlm_item_locator` fixed at selection time
(`<source>/<split>/<row>`). It is never derived from a result position.
