## 4. Manifest schema and hash behavior

`science_comparison_version: xlm-science-comparison-v1`. **All 36 keys are
required**; a missing key or an unknown key is a field-level problem and makes
the comparison INELIGIBLE. Nothing is defaulted.

| Group | Keys (validation) |
|---|---|
| Identity | `comparison_id` (slug), `title`, `description`, `status` (`frozen`; `draft_nonexecutable_no_results` is always a problem), `preregistered_at`, `parent_baseline {id, version}` |
| Design | `track` (known and certified), `scale_stage` 50m/150m/300m, `study_stage` screen/replication/confirmation, `question` superiority/noninferiority |
| Arms | `control_arm`, `candidate_arms[]`: `{arm_id, label, intervention}`. An intervention sets exactly the declared primary interventions, and each candidate must differ from control (it must be *realized*). |
| Roster | `replicate_roster[]`: `{tuple_id, role exploratory/confirmation, init_seed, training_seed, data_seed, order_manifest_id}`. Replicate identities must be unique. `order_manifest_id` is `shard_native_no_order_manifest` (pre-M5) or a 64-hex M5 identity. |
| Differences | `intended_differences` must be in the track allowlist, and consequences need their cause. `required_invariants` must include every track MUST_MATCH field (and may add recorded ones). `fixed_values` are invariant values frozen and checked against evidence (e.g. global batch 65,536). |
| Budget/LR | `training_budget_targets`; `schedule {lr_policy = target_endpoint_before_update_v1, base_lr, warmup_targets, horizon_targets, min_lr_ratio}` |
| Endpoint/metrics | `primary_endpoint {tier, planned_threshold = budget}`; confirmation uses `endpoint_confirmation`. `primary_metric {name, direction}` is `equal_domain_text_ce_nats_per_token` or `equal_domain_text_bpb`. `secondary_metrics[] {name, direction, role guardrail/descriptive, source {tier, planned_threshold, path[]}, regression_margin}`. `curve_metric {name, direction, tier, start_target, end_target = budget}` or null. |
| Margins | `practical_margin`, `noninferiority_margin` (positive, primary-metric units, or null); `margin_rationale` is required when any margin is set; `efficiency {name, direction, minimum_relative_gain}` or null |
| Inference | `confirmatory_pairs` (50m 5, 150m/300m 3; null outside confirmation); `multiplicity {family_id, family_size ≥ #candidates, guardrail_family_size ≥ #guardrails}`; `ci_level = 0.95` |
| Rules | `stopping_rule = fixed_n_all_pairs_no_early_success_v1`, `promotion_rule_version = xlm-p35-promotion-v1`, `final_checkpoint_requirement = exact_budget_endpoint_v1`, `failure_policy = failed_or_missing_pair_blocks_confirmation_v1` |
| M5 / scale | `order_robustness {required, m5_order_evidence}`; `scale_promotion {intent, prerequisite {manifest_hash, required_state}, resource_plan_ref, ablation_refs}`. A scale intent requires order robustness; a 150m/300m confirmation must name the prior-scale manifest. |

**Direction is verified, not trusted.** A registry maps each metric name to its
direction: `*ce_nats_per_token`, `*bpb` and `*perplexity` are lower-is-better;
`*acc`/`accuracy`, `suite_index` and targets/s are higher-is-better. A declared
direction that contradicts the registry is refused ("would invert it"). An
unknown metric name is refused.

**Hash.** `manifest_hash = identity_digest(manifest)` is the canonical sorted
JSON SHA-256, independent of key order. The record binds it, and the rendered
report shows it.

- Changing a margin, the family size, the roster or the primary metric gives
  a different hash; tests cover each case.
- Margins are therefore frozen inputs.
- A missing required margin is a **promotion blocker**, not a default.

## 5. Field classification model and eligibility matrix

Every one of the 52 evidence fields gets an explicit class on each track; a
test enforces that no field is left unclassified.

| Field(s) | microbatch_grouping_v1 | data_mixture_v1 |
|---|---|---|
| `microbatch_sequences` | INTENTIONALLY_VARIED | MUST_MATCH |
| `mixture_components` | MUST_MATCH | INTENTIONALLY_VARIED (declared intervention) |
| `exposure_plan_identity`, `data_trace_digest`, `per_source_exposure`, `data_input_identity` | MUST_MATCH (flattened exposure equality) | INTENTIONALLY_VARIED, only as declared consequences of changed components/exhaustion |
| `mixture_exhaustion_policy` | MUST_MATCH | INTENTIONALLY_VARIED only if declared |
| model architecture/component/parameter count/attention backend, `initial_model_state_digest`, objective | MUST_MATCH | MUST_MATCH |
| `init_seed`, `training_seed`, `data_seed`, `order_manifest_id` (pairing) | MUST_MATCH | MUST_MATCH |
| tokenizer identity, vocabulary, context, packing, scheduler, within-source order policy | MUST_MATCH | MUST_MATCH |
| global batch, budget, committed targets, `update_boundaries_digest` | MUST_MATCH | MUST_MATCH |
| optimizer, clip, schedule, LR policy, science version | MUST_MATCH | MUST_MATCH |
| precision, runtime (attention/TF32/BF16 reduction), compile, checkpointing, producer, device, runtime device name/torch, code/lock/environment | MUST_MATCH | MUST_MATCH |
| evaluation plan, evaluator identities (inventory, scoring policy, scorer), checkpoint plan | MUST_MATCH | MUST_MATCH |
| run id, plan hash, execution hash, checkpoint id, **final weights digest**, observed attention ops | RECORDED_MAY_DIFFER | RECORDED_MAY_DIFFER |

The rule is: **eligible ⇔ manifest valid ∧ track certified ∧ every
MUST_MATCH field known and equal ∧ every difference in an INTENTIONALLY_VARIED
field declared (with its cause for consequences) ∧ no evidence value
contradicting the manifest ∧ no duplicate/unregistered run ∧ no
cross-tokenizer CE primary.**

- `null` is unknown, never equal, so a MUST_MATCH field that is `null` makes
  the comparison ineligible.
- A field listed in `required_invariants` becomes MUST_MATCH even if the track
  would only record it.
- An ineligible candidate gets **no** statistics, and its decision is `INELIGIBLE`.

## 6. Pairing, replicate identity and same-seed reruns

- **Replicate identity** = `identity_digest({init_seed, training_seed, data_seed,
  order_manifest_id})`. It is read from the frozen envelope and M1 policy of
  each run, never from roster labels. A run is placed in the manifest tuple
  with the same identity; the rule is `explicit_replicate_identity_v1`.
- Pairs are never formed by list position, time, checkpoint or name.
  Shuffling the input rows gives identical candidate results (tested).
- A run whose tuple is not in the roster ("mismatched seeds", e.g. C0's init
  and data seeds with C1's training seed) is listed. Its arm's comparisons are
  **INELIGIBLE**; unregistered seeds are never added adaptively.
- **Same-seed reruns are repeats, not replicates.** Rule
  `single_at_budget_attempt_per_replicate_v1`:
  - more than one at-budget attempt of one (arm, replicate) is `DUPLICATE`,
    which makes the comparison INELIGIBLE;
  - partial or failed attempts are retries, kept visible and never counted;
  - the same evidence listed twice is refused.
- Five reruns of C0 against a five-pair confirmation give at most one pair,
  INELIGIBLE, promotion `NOT_ELIGIBLE`, and no statistics. Relabelling C0's
  seeds as C0…C4 in the roster is refused by the manifest ("a same-seed rerun
  is not a new replicate").
- **Missing pair**: `MISSING` or `INCOMPLETE`. The decision is `INCOMPLETE`,
  and promotion is PROVISIONAL (≥1 complete) or INCOMPLETE (0 complete).

## 7. Microbatch-grouping track (`microbatch_grouping_v1`)

- **Only** `microbatch_sequences` may differ, and it must be declared and
  realized by the arms (B8/B16/B32).
- These must match: global valid targets per update, budget, committed
  targets, and `update_boundaries_digest`. That digest is taken over every
  update's `(committed_before, valid_targets)` from the M1 LR receipts, which
  are checked to be contiguous and to sum to the committed count.
- The data exposure must also match: the `data_trace_digest` (the P34 chained
  per-target trace of source, doc, lineage, token offset, label, byte span and
  epoch), `per_source_exposure`, `exposure_plan_identity`, initialization,
  tokenizer, optimizer, LR contract, precision, attention/runtime and
  evaluation identities.
- **The final weights digest is RECORDED only**; grouping legitimately changes
  reduction order.
- The trace digest is the strongest *existing* evidence. It binds labels,
  order and source attribution per target, but not a separate digest of
  masks/positions per update (§22 risk 1).
- M4 selects no microbatch winner. A screen is `SCREEN_ONLY`; a future NI
  confirmation needs a frozen NI margin plus a measured cost benefit.

## 8. Data-mixture track (`data_mixture_v1`)

- `mixture_components` (weights/quotas) is the declared intervention.
- These may differ only as **declared consequences**, and only when their
  cause actually differs:
  - `exposure_plan_identity`;
  - `data_trace_digest` (global token order);
  - `per_source_exposure` (source counts);
  - `data_input_identity` (component substitution).
- `mixture_exhaustion_policy` may differ only if declared.
- Fixed: model, initialization, tokenizer, budget, update boundaries,
  optimization contract, seed pairing, `within_source_order_policy`
  (`shard_native_offset_order_v1`), scheduler, packing and evaluation
  definitions.
- Per-source exposure (valid/repeated/content/EOS targets, documents, bytes,
  epoch) is recorded in every pair's diff.
- Any additional undeclared difference is a VIOLATION, e.g. exhaustion,
  optimizer, within-source order or tokenizer (tested).

## 9. Paired statistics (`xlm-p35-paired-seed-t-v1`)

For complete pairs `i = 1..n` (sorted by tuple id):

- the raw delta is `d_i = candidate_i − control_i`, preserved as-is;
- the normalized improvement is `u_i = control_i − candidate_i` for
  lower-is-better and `candidate_i − control_i` for higher-is-better, so
  positive always means "candidate better";
- `ū = fsum(u)/n`;
- `s = sqrt(fsum((u_i − ū)²)/(n−1))` and `SE = s/√n`;
- `α_test = (1 − ci_level)/m`, where `m` is the manifest's `family_size`;
- the critical value is `t* = t_{1−α_test/2, n−1}`;
- the interval is `ū ± t*·SE`; the raw interval is its negation for
  lower-is-better.

The record also carries the sign summary and the leave-one-pair-out means
(§P). `math.fsum` makes results independent of pair order.

- **Student t** is computed from the regularized incomplete beta
  (continued fraction), with bisection on the upper tail. There is no
  statistical dependency (scipy exists only transitively under the `eval`
  extra) and no z fallback.
- **Verification:** closed forms for df = 1 (Cauchy), 2 and 4 agree to
  `rel 1e-11` at 7 tail probabilities. Table values: df 3 → 3.182446305,
  df 9 → 2.262157163, df 30 → 2.042272456.
- **Hand-computed case** (SYNTHETIC; control 3.00/3.10/3.20/3.05/3.15,
  candidate 2.98/3.07/3.19/3.02/3.12):

  | Quantity | Value |
  |---|---|
  | improvements | 0.02, 0.03, 0.01, 0.03, 0.03 |
  | mean | 0.024 |
  | sample SD | √8e-5 = 0.0089443 |
  | SE | 0.004 |
  | t_{0.975,4} | 2.776445105 |
  | improvement CI | **[0.0128942, 0.0351058]** |
  | raw ΔCE CI | [−0.0351058, −0.0128942] |

  With three pairs, t_{0.975,2} = 4.302652730.
- **n = 1:** `sd`, `SE`, `df`, `t*` and both CIs are `null`, with the note "no
  seed-level confidence interval". The decision is `NO_SEED_INTERVAL`. Two
  pairs give df = 1 with t* = 12.7062, reported as exploratory.
- **Zero variance** (n ≥ 2, `s = 0`) gives a degenerate zero-width interval,
  flagged `zero_variance`. It never decides: the decision is
  `AMBIGUOUS/degenerate_zero_variance`. Identical scores give mean 0.
- **Bonferroni:** `m` comes only from the frozen manifest and is never
  inferred from how many comparisons finished.

  | m | per-comparison level | t* (df 4) |
  |---:|---:|---:|
  | 1 | 0.95 | 2.7764 |
  | 2 | 0.975 | 3.4954 |
  | 3 | 0.9833 | — |

  In the example, m = 1 and m = 2 both give CLEAR_WIN at margin 0.01, while
  m = 3 gives AMBIGUOUS (tested). `family_size` smaller than the number of
  candidates is refused. Guardrails form their own Bonferroni family
  (`guardrail_family_size`).
- **Item bootstrap is separate.** The P17 cluster bootstrap is untouched.
  Item-level uncertainty supplied to a comparison is stored under
  `item_level_uncertainty` with `used_for_decision: false`. A narrow item
  interval leaves a wide seed-interval decision unchanged (tested).

## 10. Decision semantics (`xlm-p35-decision-v1`)

Notation: improvement interval `[L, U]`, frozen margin `p` (practical) or
`m` (NI), all positive.

| Question | Result | Condition | §P form for CE (lower is better) |
|---|---|---|---|
| Superiority | CLEAR_WIN | `L > p` | upper CI of `CE_cand − CE_ctrl` < −δ_practical |
| Superiority | CLEAR_LOSS | `U < −p` | lower CI > δ_practical |
| Superiority | AMBIGUOUS | otherwise | "positive mean, uncertain practical gain" (or negative/zero), reported separately |
| Non-inferiority | NON_INFERIOR | `L > −m` | upper CI of ΔCE < δ_NI |
| Non-inferiority | CLEAR_LOSS | `U < −m` | — |
| Non-inferiority | AMBIGUOUS | otherwise | `noninferiority_not_shown` |

- A **nonsignificant difference is not non-inferiority.** An interval
  containing 0 but reaching below −m is AMBIGUOUS (tested).
- The NI bound is the matching side of the same two-sided Bonferroni
  interval, i.e. the one-sided (1 − α/2m) bound, as §E.6 specifies.
- **Boundary rule:** a bound within `1e-12·max(1,|margin|)` of a margin is ON
  the boundary, which never satisfies a strict inequality. Floating noise can
  only make a decision more conservative (tested at `L`,
  `nextafter(L, ±)`).
- **Missing margin:** the decision is `NO_MARGIN`, and promotion is
  `NOT_ELIGIBLE` ("INELIGIBLE FOR PROMOTION"). No universal threshold exists
  in product code.
- **Efficiency** (NI questions): from declared per-run measurements,
  `gain_i = (b − a)/a` (or `(a − b)/a` for lower-is-better). It is shown only
  when the mean gain is ≥ the frozen `minimum_relative_gain` **and** its
  paired-t lower bound is > 0. Measurements are labelled operator-declared,
  since no M1–M3 receipt measures throughput.
- **Primary only.** Secondary metrics are descriptive (unadjusted, outside the
  claim family) or guardrails (which can only block). A benchmark cannot be
  the primary under promotion-v1.

## 11. Learning-curve area

`fixed_linear_target_area(points, start, end)` works on points
`(planned_threshold, actual_committed_targets, metric)`:

- it is a trapezoid over **actual committed targets** divided by the actual
  interval;
- the planned grid must contain both `start` and `end`, and points outside
  are refused;
- a missing start or end is refused and never interpolated or extrapolated;
- the actual targets must increase;
- there is no wall-time input at all.

In a comparison, both arms must have identical `(planned, actual)` grids,
otherwise the pair is `INCOMPARABLE`. Any incomplete point makes the curve
`INCOMPLETE` with no area. The area delta is descriptive and reported
separately from the endpoint (§K). Hand check: (16M, 4), (32M, 3),
(128M, 2) → (0.5·7·16M + 0.5·5·96M)/112M = 2.642857.

## 12. Evidence completeness (per run)

A run counts toward a pair only if all of these hold:

- its evidence verifies (digest; checkpoint artifact verified by the store;
  envelope identity recomputed; manifest-bound execution provenance);
- it is science-v1 (legacy refused);
- it declares status `completed`;
- it has committed exactly its budget, which matches the manifest;
- its seed tuple is known and registered;
- the primary endpoint event is COMPLETE under `first_complete_attempt_v1`,
  in the crossing lineage, with a verified receipt identity, finite metrics
  and complete coverage;
- every guardrail's source event is COMPLETE with a finite value.

A partial or missing evaluation is **never** a zero, and a missing benchmark
shows as `NOT RUN` or `PARTIAL n/N`. Failed, in-doubt and cancelled attempts
stay in `runs` with their reasons and are counted under `failures`.

An in-doubt state cannot appear in a published checkpoint: M1 refuses to
publish one. It is represented by the roster status `in_doubt`.

## 13. Promotion rule `xlm-p35-promotion-v1`

The rule is evaluated in this order. It never launches, authorizes or drafts
a job (`executes_nothing: true`).

1. Invalid manifest or ineligible candidate → `NOT_ELIGIBLE`.
2. A manifest promotion blocker (a missing margin or cost threshold) →
   `NOT_ELIGIBLE`.
3. `screen` or `replication` stage → `SCREEN_ONLY`.
4. A 150M or 300M confirmation without a verified prior-scale record in
   `PROMOTE_TO_150M` / `PROMOTE_TO_300M` (hash-verified, matching the
   manifest's `prerequisite`) → `NOT_ELIGIBLE`.
5. Complete pairs:
   - 0 complete → `INCOMPLETE`;
   - fewer than the fixed n → `PROVISIONAL`. The first three of five are
     never early success.
6. CLEAR_LOSS, or a guardrail whose interval lies beyond −margin → `REJECT`.
7. A non-success primary, or a guardrail not shown within margin →
   `AMBIGUOUS`. For NI, the efficiency benefit must also be shown.
8. At 150M/300M, not every pair improving → `PROVISIONAL` (§R).
9. Order robustness required but BLOCKED → `PROVISIONAL` (§14).
10. Otherwise → `CONFIRMED_{50M,150M,300M}`.
11. With `scale_promotion.intent`, below 300M, a declared resource plan, and
    (for 50M) declared ablation references → `PROMOTE_TO_150M` /
    `PROMOTE_TO_300M`. These are recorded as "declared references; not
    verified by M4".

The staged requirements, as enforced:

- **50M**: five fresh confirmation tuples (C0–C4), 1B targets, confirmation
  endpoint, Bonferroni family, guardrails, clear win (or NI plus efficiency),
  and order robustness for promotion.
- **150M**: the prior 50M `PROMOTE_TO_150M` record, three fresh tuples, 3B,
  all pair effects positive, CI and margin.
- **300M**: the prior `PROMOTE_TO_300M` (a complete 150M confirmation), three
  fresh tuples, 6B.
- One 50M screen used as a prerequisite is refused.
- Not every hypothesis must reach larger scales; `intent: false` stops at
  `CONFIRMED_*`.

## 14. M5 document-order dependency

Before M5 every run's evidence carries `order_manifest_id =
shard_native_no_order_manifest`, and `within_source_order_policy =
shard_native_offset_order_v1`. `order_robustness()` returns `SATISFIED` only
when all of these hold:

- the manifest's `m5_order_evidence` has kind
  `m5_independent_order_manifests_v1`;
- it names ≥ 2 distinct order manifests;
- every paired tuple actually carries one of them, never the sentinel.

Otherwise, when the requirement is declared, the result is `BLOCKED` (NOT
RUN). Tested cases:

- a clear 50M win with a scale intent → `PROVISIONAL` with blocker
  `order_robustness`;
- a placeholder `{"kind": "source_seed_variation"}` → BLOCKED ("cannot
  satisfy");
- the M5 kind with sentinel runs → BLOCKED.

The promotion tests that reach `PROMOTE_TO_150M` do so only with **simulated
future M5 evidence**, authored in the test with two synthetic order ids.
M4 implements no document reordering.

## 15. CLI

```
uv run --offline --locked --extra cuda --extra eval xlm experiment compare --comparison <manifest.json> --runs <runs.json> --output <dir> [--prerequisite <prior comparison.json> ...]
uv run --offline --locked --extra cuda --extra eval xlm experiment report --record <dir>/comparison.json --output <dir2>
```

`--runs` (`xlm-science-comparison-runs-v1`) lists
`{label, arm_id, status, failure, checkpoint (absolute path | null), measurements {name: {value, source}}, synthetic}`.

- `compare` extracts evidence from each checkpoint. The parameter count comes
  from the existing meta-device counter, which needs torch; if it is
  unavailable the count stays unknown and the comparison INELIGIBLE.
- A checkpoint whose evidence is refused becomes a visible failed attempt
  with the exact reason.
- `compare` writes `comparison.json`, `report.md` and `summary.csv`. It exits
  1 when the manifest is invalid or any candidate is ineligible; the record
  is still written.
- `report` verifies the record hash and embedded manifest hash, then
  re-renders byte-identically. It refuses an altered record or a legacy P17
  output.
- Neither verb trains, schedules or authorizes. The existing `xlm compare` /
  `xlm promote` (P17) are unchanged.

## 22. Risks and open questions

1. **Microbatch fairness evidence.** The P34 per-target trace digest binds
   label, order, source, doc, offset, bytes and epoch for every committed
   target, and the LR receipts bind update boundaries. There is no dedicated
   per-update digest of input ids/masks/positions. §E asks for these on
   authored windows before the B8/B16/B32 study. If a stronger receipt is
   wanted, add it before the study, as a new evidence field that is
   MUST_MATCH on the microbatch track.
2. **Throughput/VRAM are operator-declared.** No M1–M3 receipt measures them.
   An NI efficiency claim therefore rests on declared measurements, and the
   report labels them so. A receipt-bound timing capture is future work.
3. **Hardware identity** is the runtime receipts' device name, the torch
   version and the installed-environment digest. The CUDA driver and cuDNN
   are not recorded by M1, so they cannot be compared.
4. **Real-run shape conformance.** The reader mirrors the M1–M3 shapes; its
   constants are AST-checked. The first real science-v1 checkpoint should be
   run through `extract_run_evidence` on the CUDA environment to confirm that
   runtime receipts and ledgers match the authored fixtures.
5. **Scale prerequisites** (`resource_plan_ref`, `ablation_refs`) are declared
   references, not verified artifacts.
6. **Margins.** No valid numerical margin can be derived from existing data
   (§P). Both drafts leave them null for the user.
7. The existing `escape_markdown_text` double-escapes `<` (`&amp;lt;`). This
   is safe but cosmetic; the legacy function was left unchanged.
