## Retained implementation

1. Token publication writes a private staged shard, flushes and fsyncs binary,
   index, counters and manifest, then publishes payloads and the manifest last.
   A bounded writer lock prevents concurrent publication; an existing payload
   makes the destination immutable. POSIX also fsyncs directories. Failure can
   leave an orphan payload without a manifest; retry must use a fresh destination.
   Windows file contents are synced, but directory-entry power-loss durability
   remains unproven. Manifest-last visibility is not a universal power-loss claim.
2. Tokenizer fitting validates the same selected documents and spools normalized
   UTF-8 text to a length-framed temporary file. Input ordering, newline-separated
   fit identity, caps and split rejection order are unchanged. Backend iteration
   no longer duplicates the selected corpus as Python text objects. CLI fitting
   uses a count pass and a streaming fit pass. Fit selection retains only split
   and UTF-8 byte count per ID, preserving original last-ID-wins behavior.
3. Native offset batches are opt-in, bounded by at most 512 documents and 1 MiB
   text (one oversized document travels alone under the caller's record cap).
   Default scalar behavior remains. The BPE object is reused; the span algorithm,
   special-token framing and IDs are unchanged. Offset JSON is encoded once and
   the same bytes are written and hashed. Binary blocks remain 4,096 IDs.
4. `xlm.data.parallel_tokens` verifies P27A manifests and gives each spawned
   process a fixed lane of whole shards. Each worker initializes one tokenizer,
   processes documents sequentially and writes deterministic shard artifacts.
   Only bounded result records cross the process queue. Missing/failed/duplicate
   groups fail the operation. Parent assembly follows source-shard order and
   rebases exactly three index coordinates while preserving authoritative spans
   and metadata. Final binary, index, counters and manifest match the scalar
   writer, so cross-shard packing carry remains unchanged.
5. Optional `TokenMapCache` verifies artifact identities and hashes on admission,
   reuses read-only maps, checks file identity on access and closes mappings and
   handles on LRU eviction or explicit context exit. No memoryview escapes.
   Replacement/disappearance fails instead of serving stale bytes. It is
   instance-owned and bounded; `MixtureBatcher(max_open_shards=0)` remains the
   default because cached maps did not beat ordinary file reads consistently.
6. Mixture indexing fills contiguous document ranges instead of looking up every
   token. Trimming a speculative window anchors the index cache at its last
   consumed document, avoiding repeated scans for short documents. Trace hashing
   uses the same canonical JSON and SHA chain; only fixed primitive records take
   a schema-proven shortcut around recursive validation. Malformed shapes use
   the original validator. RNG, schedule, cursor schema and replay are unchanged.
7. Causal packing finds sparse BOS/PAD positions with native `list.index` and
   falls back to the original scan for dense controls. Masks, targets, context,
   attribution, positions and carry are unchanged.

Parallel defaults are 100,000 documents, 256 MiB input, 8 MiB per record,
2 GiB output including worker scratch plus final output, 900 seconds and 3 GiB
aggregate sampled RSS. Assembly splits its output allowance between parts and
final output. Tokenizer files are capped at 64 MiB each. Worker allowances are
apportioned by input bytes and can reject an unusually expansive shard. The
pipeline allows 3 GiB disk for parallel input sharding/assembly (2 GiB otherwise).
These are application guardrails, not OS reservations; RSS/elapsed checks are
sampled/cooperative. Assembly has a byte bound but no independent hard OS deadline.
Callers must supply the already selected single-source split; the module does
not silently filter or change membership. Existing general `data tokenize` CLI
materialization is unchanged; the new explicit module is the bounded shard path.

## Profiles and decisions

The 10k offset writer profile took 9.07 s under cProfile. Native encode was
3.17 s own time; the Python offset wrapper was 1.77 s own / 6.16 s cumulative,
JSON encoding 0.93 s, dictionary lookup 0.66 s, append 0.49 s, byte coverage
generator/sum about 0.80 s, struct packing 0.05 s and SHA updates 0.05 s.
Writing was about 0.13 s. Nested times overlap and profiling adds overhead.
The committed profile text includes fsync, manifest and object-construction costs;
these are not fabricated independent wall-time allocations.

The retained 100k writer profile reports native encode 39.70 s own time,
span construction 21.90 s own / 36.20 s cumulative, JSON encoding 11.83 s,
dictionary lookup 7.79 s, list append 6.20 s, buffered writes 2.65 s,
struct packing 0.61 s, SHA updates 0.54 s, and four fsyncs totaling 0.17 s.
It also contains substantial sampling-thread/profile overhead (about 9.41 s
attributed to waits). It is diagnostic attribution, not an unprofiled speed claim.

The actual 100k probe takes 40.86 s native encode, 36.40 s IDs only and
48.36 s with offsets. Serial native batches 16/64/128/512 take
35.98/36.65/36.04/44.31 s. Warmth/order variability prevents treating tiny
differences as improvements. A full writer with batch 128 and eight native
threads takes 50.72 s at 249 MiB RSS, providing a measured lower-memory option.
Eight is the fastest tested worker count: scalar shards take 30.93 s and
serial-native batches take 30.41 s, a small additional difference.
Final assembly and input preparation add meaningful time. Do not substitute
the shard-only result for end-to-end throughput.
Final assembly alone takes 8.331 s. Parent logical OS read/write counts for the
100k pipeline are 2,116,167,154 / 1,566,980,732 bytes before and
3,604,180,887 / 1,753,931,198 after; child I/O is excluded and these are not
physical disk traffic. Temporary disk peaks at 2,150,931,249 bytes. Final artifact
totals differ by a few bytes in elapsed-time metadata; authoritative files match.

Authoritative JSON contains document boundaries, byte spans, lineage, source and
coverage required by C06/C07 and exposure accounting. A compact auxiliary index
was investigated but not implemented: serialization is a minority of writer
cost, the loader's measured hot cost was trace validation/index rescanning, and
a second versioned hash-bound format adds publication and regeneration work.
NumPy was unavailable; no package was installed to pursue it.

Binary block probes use a bounded repeated 128-document token sample, not the
whole 100k output: 4k/16k/64k/256k blocks took about
0.129/0.125/0.124/0.143 s in the 100k probe process. There is no robust gain
justifying a larger default. uint16/uint32, little endian and invalid-ID
validation remain exact. The scalar 10k comparison includes publication fsync
cost together with the batch dispatcher; it does not isolate a causal fsync tax.
Fsync counts are measured; no durability step was removed for speed.

A prefix-sum byte-span experiment was removed: paired 10k results were
4.954 -> 4.869 s, then 5.008 -> 5.029 s in reverse order. This is noise-level.
`p29b-oracles.json` preserves that rejected trial; final-oracle results separately
describe the retained code. No timing from the rejected version is a final claim.

Tokenize/pack fusion was rejected without adding another product format. The
canonical artifact must still exist, token verification/rereading is small, and
packing depends on mixture/scheduling/resume policy rather than just producer
shard boundaries. Materializing packed copies would add disk and freeze consumer
policy. The measured packing hot loop was optimized in place instead. No fused
training-shard benchmark is claimed. Isolated packing of 10,000 windows (5.13M
token visits) was 0.896/0.887 s before and 0.414/0.414 s after, with all
`PackedWindow` fields hashed outside timing and dense/partial controls exact.
The final pinned-reference repeat gives 0.787/0.731 s before versus
0.333/0.335 s after. Both paired orders agree on the improvement.

Raw 10k repeated reads: file reads 1.330 s, open/map per read 1.927 s,
verified persistent maps 1.427 s plus 0.479 s admission. Open/map counts are
10,000/0, 10,000/10,000 and 0/0 steady state (one admission map). RSS is
35.5/35.6/45.4 MiB; observed Windows page faults 497/22,443/2,526.
Persistent mapping is useful against repeated mapping, not a demonstrated
universal winner. Single-source `TrainingBatcher` keeps ordinary file reads.

The mixture profile located recursive trace validation as the dominant CPU cost
(13.29 s cumulative identity hashing in a combined 40-step profiled run).
Unprofiled 50-step default loader improved from 9.458 s to 7.060 s before the
packing change and 5.062 s in the final run. These are single observations under
varying host conditions; the incremental difference is not assigned entirely to
packing. Full batch/cursor digest is
`945c99b50ead4ffc415c4f3881ab56164baa2ff64d173e9884d6c9b0c853e5aa`.
A 500-step trial was stopped after roughly seven minutes and returned exit 1;
it is not a successful benchmark. The harness now caps this experiment at 100
steps/180 seconds. Its repeated-index-scan finding motivated the anchor repair.

Fit selection Python heap fell from 33,644,906 to 3,161,986 bytes on 10k
authored documents. Text preparation fell from 24,411,089 to 27,256 traced
Python bytes, while time rose 0.328 -> 0.626 s due to spooling. These are
`tracemalloc` peaks, **not** native trainer RSS. The Rust merge frontier remains
backend-owned. Scratch grows with selected canonical bytes plus eight bytes per
document. Full pool assembly still retains accepted documents because its API
returns them; replacing that API is deferred. No research tokenizer was fitted.

## Durability, GPU readiness and remaining work

`ArtifactStore.publish_artifact` still writes checkpoint payloads, manifest and
`_COMPLETED`, then renames without explicit payload/manifest fsync. It was audited,
not modified. Recommended repair: sync payloads, sync manifest and completion
marker, sync containing directories bottom-up before/after rename on supported
platforms, and add failure-injection tests plus budget checks. Define and verify
Windows directory durability separately. Do this before asynchronous checkpoints.
Token writer visibility/fsync tests do not certify checkpoint power-loss safety.

Current training transfers use synchronous `.to(self.device)` from ordinary CPU
buffers; pinned buffers, nonblocking transfers, double buffering, stream overlap
and persistent loader workers are not implemented. `benchmark_h2d.py` is an
operator-only transfer experiment, bounded to 64 MiB, 1,000 iterations and a
60-second cooperative deadline. This CPU build exits 77 (`NOT RUN`); no GPU
timing, overlap gain or training speedup is inferred.

Cleaning becomes the dominant measured pipeline stage. Existing P29 profiles
identify language/repetition/PII work; cleaning was not changed in this milestone.
Its thresholds and scientific decisions require a separate measured change.
Other open limits: final token assembly, trace SHA/JSON per target, Python index
objects, native BPE training memory, full pool text retention and Windows directory
durability. Million-document tokenization, real sources, GPU training, official
evaluation and full offline acceptance were not run.
