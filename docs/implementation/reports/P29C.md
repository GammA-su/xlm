# P29C — exact cleaning performance

The authored 100k single-worker cleaner improved **70.399 → 53.241 seconds
(24.4% less wall time)**; 10k improved **7.965 → 5.918 seconds (25.7%)**.
The full frozen pipeline with unchanged worker settings improved **160.558 →
144.719 seconds (9.9%)**. These are bounded local fixture measurements, not
production speedup or live publisher compatibility claims.

With **explicit eight-worker cleaning**, the final pipeline is **111.688 s**:
29.5% below the historical P29B **158.430 s**, and 30.4% below the fresh control.
This combines the new exact loops with already-existing process parallelism;
the entire improvement is not attributed to new algorithms. Token workers stay
at eight in all full-pipeline runs. Peak tree RSS is 2,122.1 MiB final versus
2,153.5 MiB fresh baseline, because token preparation already sets the peak.

## Retained changes and allocations

**Language:** lower the whole ASCII text once before the unchanged word regex.
Unicode retains the original regex-then-lower order, because lowercase can expand
or change boundaries. Word classes, stop words, thresholds, confidence and the
optional detector are unchanged. Paired 10k extraction/count microbenchmarks were
0.549/0.595 seconds before versus 0.483/0.542 after; full 100k language-stage
telemetry moved 8.433 → 8.176 s. This is a modest gain, not the main speedup.
No batch API exists for the default heuristic; an external detector/model was
not installed or downloaded. Existing initialization already occurs per worker.

**Repetition:** stream exact five-word tuples with `zip`/`islice`, eliminating
each temporary list slice and Python generator iteration. Reuse cached words
when the full text fits the unchanged 50k-character analysis cap; keep the exact
prefix split otherwise, including partial words at the cap. Reject obvious
non-separator lines by their first stripped character before constructing a
whole-line character set. Markdown `---`, tables and legitimate dash runs keep
their existing grammar. Python tuple equality still resolves hash collisions;
there is no probabilistic approximation or rolling hash.

Paired n-gram microbenchmarks: 0.794/0.659 → 0.425/0.484 s per 10k. Traced Python
allocation peak on a 100-document prefix: **83,156 → 58,978 bytes**. Full repetition
telemetry: **13.339 → 7.777 s**. Separator whole-text probe: 0.131 → 0.0023–0.0027 s;
that microprobe is not the full filter. The recorded pre-change reference called
the original helper; the final standalone probe spells out the equivalent old
grammar so future runs do not accidentally call the optimized helper.

**PII:** require each regex's necessary literal before scanning: `@` for email,
`hf_`, `AKIA`, `ghp_`, the private-key/canary prefixes, `-` for SSN, and lowercase
`bearer` for the case-insensitive bearer expression. Pattern matching, iteration
order, domain parsing and sequential redaction remain unchanged. Unicode SSN
digits remain supported. Placeholder counts and real-domain detections preserve
order; `example.com` and its subdomains remain exempt, lookalikes do not.
No secret previews are added. Paired 10k detection microbenchmarks:
0.856/0.845 → 0.113/0.135 s. Full PII stage **9.402 → 1.307 s**.

**Shared features:** existing lazy lines/words/character caches already cover
the useful overlap and invalidate by text identity after a transforming stage.
Repetition now uses the existing words cache. Additional lowercase/sentinel
cache state was not justified by measured cost. Line duplication sets still have
exact semantics. No process-global scratch buffers or experiment state were added.
Language's traced prefix peak only changed 45,390 → 44,870 bytes; no large memory
claim follows. Full long-record allocation counters are in the raw report.

## Workers, shards and assembly

The [complete scaling table](../evidence/P29C/RESULTS.md) compares workers
1/2/4/6/8 on both versions. Optimized 100k wall times are 53.241, 37.096, 25.505,
21.271 and 20.256 s. Six workers use **1,542.5 MiB** sampled tree RSS; eight use
**1,982.1 MiB** for only 4.8% less wall time. One worker uses 227.7 MiB. Static
eight-worker shard sizes 1/4/16 MiB take **25.437 / 20.256 / 22.575 s**. Recommend
explicit 4 MiB shards and six workers when memory matters, eight for this fixture's
lowest measured latency. Defaults are unchanged; there is no autotuning.

The frozen benchmark imports Torch in spawned children through its shared
measurement harness. Its RSS and startup costs include those imports and are
not intrinsic requirements of the heuristic cleaner. Worker-body CPU excludes
interpreter bootstrap. Parent-plus-worker CPU counts a one-worker body only once.
Busy wall minus CPU is a **non-CPU residual**, not an OS wait measurement.
Dispatch-to-start includes planning, imports, process creation and queueing;
pure spawn time and OS idle time were not independently isolated.

Optional `run_sharded_clean(..., scheduling="dynamic")` dispatches complete units
with at most twice the worker count pending. Each process reuses its initialized
pipeline. Results are sorted by unit index before publication; missing/duplicate
units and failed futures fail the operation. Static remains the default.
Mixed 100k dynamic takes 21.876 s versus static 20.256 s: reject it as the mixed
default. On 128 approximately 1 MiB documents with unequal acceptance/work per
lane, four-worker static/dynamic take **33.508/29.210 s**. Reverse-order repeat:
dynamic/static **21.540/27.182 s**. Both pairs favor dynamic, but large between-run
variation prevents a precise universal speedup claim. The initial static busy
range 12.17–21.38 s narrows to 16.95–17.52 s; the CJK rejection lane is the cheaper
lane, not necessarily the expensive document type. Memory remains about 1.15 GiB.

Existing worker-local writing, buffered quarantine, ordered concatenation,
verification, atomic publication and fsync are retained. Smaller shards add
scheduling, file and fsync costs. Accepted assembly is measurable but much smaller
than filters; quarantine assembly is tiny. Sharded-output runs include separate
assembly and verification timers. No extra payload reread was introduced into
production, and no durability check was removed. Windows directory-entry
power-loss durability remains the previously documented limitation.

Measured unprofiled accepted concatenation is 1.542 → 1.498 s before/after;
quarantine concatenation is 0.058 s in both. One-worker 100k fsync calls remain
87. At 10k, output-shard assembly takes 1.579 s with one worker and 1.367 s with
four, including 0.203/0.195 s verification. Shard hashing remains part of those
assembly/verification costs. Parent read/write counters are cache-aware OS I/O,
not physical-disk traffic; raw reports retain them separately from worker timing.

Each full 100k pipeline retains about 1.408 GB and sampled a 2.151 GB temporary
peak including token scratch, below its 3 GiB job cap. Cleaner caps are 900 s,
3 GiB RSS, 512 MiB input and 2 GiB output/scratch. At handoff all P29C artifacts
retain about **7.50 GB** combined, including inputs and all compared runs.
Caps apply per job, not to aggregate retention; no prior data was deleted.
RSS sampling is 100 ms and child/disk discovery one second. Single-worker disk
is checked at stage completion, so its reported peak does not measure temporary
scratch. Fixed authored record/count bounds constrain these jobs; these are
application guardrails, not OS storage reservations or universal production limits.

One-worker parent CPU falls **60.891 → 46.312 s**. At eight workers, parent plus
worker-body CPU falls **82.641 → 59.844 s**; bootstrap CPU is excluded. Increasing
optimized workers from one to eight trades 46.312 → 59.844 s of this measured CPU
for lower wall time and about 1.75 GiB more RSS. The 10k profile itself did not
improve in wall time (10.933 → 11.033 s); it is attribution evidence, not a speed
claim. Unprofiled pairs and both reverse-order microtrials are reported.

## Rejected experiments and stopping point

- Stop-word Counter: 0.594/0.651 s versus whole-text lowercase 0.483/0.542;
  extra dict allocation loses on these documents.
- Integer word ordinals for exact n-grams: 0.625/0.603 s and 65,796-byte prefix
  peak, worse than exact tuple zip. Rolling hashes/interning/reusable arrays add
  complexity without evidence of a better remaining bottleneck.
- Mixed-Unicode C-backed character candidate: 0.142/0.152 → 0.108/0.094 s per
  10k, under 1% of cleaner wall; rejected to avoid added Unicode complexity.
- Dynamic dispatch as default and 1/16 MiB shards: measured slower on mixed input.
- Shallow document serialization: not retained; public conversion must detach
  mutable metadata. A separate producer-only serializer needs its own exactness
  and ownership contract. Recursive conversion remains a meaningful cleaner cost.
- Normalization, HTML, quarantine and additional cached sentinels have
  insufficient expected savings for a broader rewrite. No new dependency.

The next cleaner investigation should target the educational-keyword regex,
with exact Unicode/case/boundary tests and a corrected diagnostic timer; then
producer-only serialization and remaining language word extraction. The final
caller audit shows this length-filter cost remains meaningful; it was not
optimized or claimed negligible. At pipeline level, token
preparation becomes the largest stage once explicit cleaning parallelism is used;
profile its worker bootstrap/final assembly before adding more workers. No
production throughput claim is supported until separately authorized real-source
pilots exist. Optional 250k run NOT RUN: 100k plus the 128 MiB uneven-work fixture
were sufficient for these bounded implementation decisions.
