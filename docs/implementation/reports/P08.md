## 2. Implemented Architecture & Components

### 2.1 Acquisition Plan & Authorization Model (`src/xlm/data/acquisition/plan.py`)
- **`AcquisitionPlan`**:
  - Captures source ID, view ID, provider, repository, immutable snapshot revision, acquisition mode (`whole_file` vs `selected_records`), selected files, sampling frame, bounded limits, and output artifact ID.
  - Implements `compute_behavioral_hash()`: computes an invariant SHA-256 digest over the behavioral attributes of the plan (excluding non-semantic timestamps or authorization payloads).
- **Separated Pilot vs Production Authorization**:
  - Pilot plans (`is_pilot: True`, <= 256 MiB transfer, <= 25,000 records, <= 2 GiB output disk) require operator pilot approval (`is_pilot_approved: True`).
  - Production plans (`is_pilot: False`) strictly require cryptographic authorization matching `compute_behavioral_hash()`.
  - Operator approval cannot bypass unadmitted catalog sources or direct-source denylists (`DirectSourceDeniedError` on `HuggingFaceFW/fineweb` and `HuggingFaceFW/fineweb-edu`).
- **Atomic Plan Persistence**:
  - `save_acquisition_plan` and `load_acquisition_plan` serializing and validating schema consistency.

### 2.2 Dedicated Acquisition Receipt (`src/xlm/data/acquisition/receipt.py`)
- **`AcquisitionReceipt` & `AcquiredFileInfo`**:
  - Records plan ID, timestamp, eligibility tag (`pilot_only` vs `production_eligible`), acquired file paths, byte sizes, row/record counts, locally computed SHA-256 digests, provider checksums, and independent expected checksums.
  - Captures resource usage accounting: total transferred bytes, cache hits, requests made, elapsed seconds, temp disk bytes, and output disk bytes.

### 2.3 Storage Capacity Manager & Atomic Disk I/O (`src/xlm/data/acquisition/disk.py`)
- **`StorageCapacityManager`**:
  - Tracks cumulative transferred bytes, uncompressed bytes, temporary scratch disk bytes, and final output disk bytes.
  - Enforces physical disk headroom checks (`shutil.disk_usage`) against configurable safety reserves (default 1 GiB free disk required).
  - Immediately raises `BudgetExhaustedError` if any cumulative ceiling or disk limit is breached.
- **`AtomicFileWriter`**:
  - Manages partial file streams (`.part`), explicit `fsync` flushing before rename, prefix hashing for crash consistency, truncation of unverified trailing bytes, and atomic rename to final paths.

### 2.4 Progress Journal & Crash-Consistent Resumption (`src/xlm/data/acquisition/progress.py`)
- **`ProgressJournal`**:
  - Implements versioned (`schema_version: 1`) state machine: `PENDING`, `IN_PROGRESS`, `INTERRUPTED`, `COMPLETED`, `FAILED`.
  - Tracks per-file progress: status, verified durable bytes downloaded, total expected bytes, ETag, last modified timestamp, and chunk hash.
  - Periodic atomic flush via atomic temporary file rename (`.tmp` -> `.progress.json`).
  - **Reconciliation on Restart**:
    - `reconcile_with_disk` inspects disk files against journal state on startup.
    - If a partial file contains trailing unjournaled bytes from a crash or killed process, it is truncated down to the last verified durable offset before resuming.

### 2.5 Bounded Resumable Fetcher & Safety Guards (`src/xlm/data/acquisition/fetcher.py`)
- **`BoundedFetcher`**:
  - Governed by plan limits and inter-process concurrency locks (`FileLock` in `data/scratch/locks/<plan_id>.lock`). Concurrent invocations raise `AcquisitionLockHeldError`.
  - Safe network transport via `SafeRedirectHandler` ensuring redirects remain within allowlisted domains (`huggingface.co`, `raw.githubusercontent.com`, `127.0.0.1`, etc.).
  - Bounded request deadlines, exponential backoff with jitter on 429 (`Retry-After`) and 5xx transient server errors.
- **Source Drift Detection & Range Resumption**:
  - Resumption uses HTTP `Range: bytes=<offset>-` with `If-Range: <etag>`. Weak ETags (`W/"..."`) are explicitly excluded from `If-Range`.
  - Upstream drift detected via HTTP 412 or mismatched Content-Range start offsets immediately raises `SourceDriftDetectedError` to halt execution without corrupting files.
  - Detects early socket dropout (when server sends fewer bytes than `Content-Length`/`Content-Range` without raising an exception) and automatically recovers via Range retry.
  - When a server ignores `Range` (returns 200 OK), cleanly truncates the partial file and restarts from byte 0 without concatenation corruption.
  - Cache hits: pre-existing verified files are validated and recorded without incurring network transfer.
- **`BoundedDecompressor` & `_CountingReader`**:
  - Streams decompression in bounded chunks, tracking raw compressed input bytes vs decompressed output bytes.
  - Enforces maximum expansion ratio (`max_ratio`, default 15.0x) and max uncompressed byte ceiling, raising `DecompressionBombError` on zip-bombs.

### 2.6 Format Verification & Artifact Store Publication (`src/xlm/data/acquisition/verifier.py`)
- **`AcquisitionVerifier`**:
  - Validates physical file existence, exact byte sizes, and SHA-256 digests against independent expected checksums.
  - Validates Parquet schemas (using PyArrow table metadata) and JSONL line formatting.
  - Publishes verified raw data into P01 `ArtifactStore` as immutable `raw_dataset` artifacts (`raw_<source_id>_<view_id>`).
  - Post-publication verification detects any subsequent file corruption or tampering.

### 2.7 CLI Commands (`src/xlm/cli/data_cmd.py`)
- `xlm data plan`: Compiles and validates an acquisition plan with sampling parameters, mode, bounded limits, and pilot/production authorization.
- `xlm data fetch`: Executes bounded resumable acquisition governed by progress journal and process locks.
- `xlm data status`: Inspects progress journal, cumulative resource consumption, and per-file completion status (with `--json` support).
- `xlm data verify`: Verifies raw acquired files against format/checksum integrity and publishes immutable `raw_dataset` artifacts into the P01 artifact store.
